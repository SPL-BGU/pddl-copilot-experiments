What went wrong on the way, and the fix for each (all on the branch):

1. **Cluster home quota (23630463, 23630464).** Inside apptainer `HOME` is the real home,
   so model downloads went to `~/.cache/huggingface`, never to job scratch. Three new
   downloads filled the quota and every job died mid-download with no error. Fix `5f61513`:
   new models set `HF_CACHE_IN_JOB=1` (download to scratch) and `HF_REVISION`. Seven unused
   cache folders were deleted with Omer's approval.
2. **Ministral rejects `chat_template_kwargs`** (vLLM's Mistral tokenizer raises on any
   request carrying it; the harness sends it whenever thinking is on or off). Ministral has
   no thinking mode, so it runs with `--think-modes default`, which sends none. No code change.
3. **Ministral accepts only 9-character alphanumeric tool-call ids**; the client replayed
   `call_<n>_<i>`. Fix `02eed06`: `TOOL_CALL_ID_STYLE=mistral9` for this model only.
4. **Ministral's context-overflow message gives the exact prompt count**, a wording the
   client did not parse, so 102 of 960 trials became `exception` instead of being retried
   with a smaller answer budget. Fix `d9b077a`. No stored row of `sweep5v2-live` or
   `delivered-rerun` holds an overflow error, so the older models are unaffected.

## D1d. The JSON constraint

**Cause, from vLLM's source at v0.20.2:** the chat request has no `guided_json` field, and
unknown fields are dropped with a DEBUG-level log only (`OpenAIBaseModel`, `extra="allow"`).
The field that binds is `structured_outputs={"json": schema}`. The branch adds it as an
opt-in (`--json-constraint structured_outputs`, cell `no-tools-jsonbound`, set per run by
`$PDDL_JSON_CONSTRAINT`); the default request is unchanged.

Probe: Qwen3.5-9B, unaided, thinking off, one item per domain, both cells in one window
(jobs 23630577 plain, 23630578 bound).

| task | n | answer starts with `{` (plain / bound) | harness online grade (plain / bound) |
|---|---|---|---|
| solve | 60 | 0% / 100% | 0.10 / 0.05 |
| validate_domain | 120 | 0% / 100% | 0.51 / 0.57 |
| validate_problem | 120 | 0% / 100% | 0.57 / 0.52 |
| validate_plan | 120 | 0% / 98.3% | 0.83 / 0.57 |
| simulate | 60 | 0% / 100% | 0.05 / 0.12 |

The constraint binds. Two of 480 bound answers escaped it (validate_plan, both cut at the
output cap, both starting "VERDICT: VALID"); no grammar warning in the serve log. The likely
cause is the server treating those outputs as unfinished reasoning (the structured-output
config carries `reasoning_parser='qwen3'`), unconfirmed. Binding the format also moves the
score, in both directions; validate_plan falls by 26 points in this slice. So the JSON
control measures a different condition, not a format fix, and the prereg should say so.

## Consequences for the extension prereg (D1f)

1. Ministral and Llama run with `--think-modes default` (neither has a thinking mode).
   **Open (Omer):** GPT-OSS always reasons; which effort level stands for its wave-1 cells.
2. **Open (Omer):** Llama weights from unsloth's ungated copy, or Meta's gated repo (needs
   access and an HF token on the cluster).
3. Context room: 16K, 32K and 64K are all feasible for the headline models on rtx_6000.
4. JSON control: `structured_outputs`, with the 2-in-480 escape reported as a known leak.
5. The official Gemma weights need rtx_pro_6000 (BF16, about 52 GB), a different GPU class
   from the AWQ build; serving parity between the two classes is worth one sentence.
