\begin{abstract}
Planners and validators are correct by construction, and language models can now
call them as tools. We ask three questions about that access. Do the tools help a
model on planning-related tasks? Does the model choose the right tool? Does it use
what the tool returns? We evaluate five open-weight and two frontier models on five
PDDL tasks, with and without a suite of seven planning tools, and a deterministic
oracle grades the final answer each model delivers. The tools help on most measures.
With them the models deliver a valid plan in $77$--$95\%$ of trials, against
$21$--$29\%$ without, and verdict errors on plans fall for four of the five models
measured. The benefit shrinks as problems grow, and state traces degrade with length
in every model. Models usually choose the right tool, but one calls the plan validator
in only $20\%$ of trials until a single sentence tells it to, and on plan generation
models often add calls they do not need. Using the output is the weak point for long
answers: almost no verdict is lost, $5$--$13\%$ of correct plans are lost, and the
open-weight models lose $70$--$91\%$ of correct state traces, mostly because the
tool's result fills the context window and leaves no room for the answer. On
PlanBench, the same tools lift an obfuscated benchmark from $0$ to $72\%$. The study
grades $273{,}600$ open-weight trials over public and renamed domains, and a
pre-registered rerun of $47{,}040$ trials that stores every answer in full.
\end{abstract}

\section{Introduction}
% DRAFT 2026-06-14 (goal 1, partial).
% Findings preview must match Results; no "first" claims.
Large language models are increasingly deployed as agents that call external
tools, and automated planning is an unusually clean setting in which to ask
whether that helps. Decades of research have produced planners and validators that
are \emph{correct by construction}: a plan a sound solver returns provably reaches
the goal, and a verdict a sound validator issues is sound
\citep{helmert2006fastdownward, howey2004val}. If a language model can simply
\emph{call} such a tool, it should be able to offload the parts of a PDDL
task (search, state tracking, and plan checking) on which language models are
known to be unreliable \citep{valmeekam2023planbench, kambhampati2024llmmodulo}.
Whether this actually helps, whether the model picks the right tool, and whether it
then uses what the tool returns, are the questions we study.

These questions are not settled. One line of work tests LLMs \emph{as} planners.
Earlier models fell well short of solvers \citep{valmeekam2023planbench}, and the
newest frontier reasoning models are reported to rival strong planners on freshly
generated tasks \citep{correa2025frontier}. Both results describe the model alone. A
second line uses LLMs as \emph{formalizers} that translate language into PDDL for a
downstream solver \citep{liu2023llmp, tantakoun2025survey}, where the solver is always
called. A third measures tool-use competence without a planning oracle
\citep{bfcl2025}. These lines leave open what happens when the same model is given
sound planning tools that it is free to call: whether its answers improve, which tool
it calls, and whether the tool's result reaches its final answer.

We evaluate five PDDL tasks (\emph{solve}, \emph{validate\_domain},
\emph{validate\_problem}, \emph{validate\_plan}, \emph{simulate}) on five open-weight
models from the Qwen and Gemma families and on two frontier models, Claude Haiku~4.5
and Claude Sonnet~4.6. Each model answers every task without tools and with a suite of
seven planning tools offered through the Model Context Protocol, under a plain prompt
and under a prompt with one added sentence that names the tool. A deterministic oracle
grades the final answer the model delivers, and every proportion carries a confidence
interval. The main sweep holds $273{,}600$ open-weight trials over the public domains
and over a renamed copy that controls for memorized domains. That sweep stored only
the first $500$ characters of each answer, so a pre-registered rerun of $47{,}040$
trials with answers stored in full supports every comparison that needs the complete
answer. We organize the study around three research questions.

\emph{RQ1: do PDDL tools help an LLM do planning-related tasks?} On most measures they
do, and less as problems grow. Without tools the models solve $21$--$29\%$ of the
planning problems, and with the tools they deliver a valid plan in $77$--$95\%$ of the
trials. Verdict errors on plans fall with the tools for both Qwen models and both
Claude models, and stay where they were for the one model that seldom calls the
validator. State traces are the hard case. Their accuracy falls with the length of the
trace in every model, and for one model the tools make them worse. A plan delivered
with tools is almost always the planner's plan, so its length is the planner's.

\emph{RQ2: does the LLM choose the right tool?} When a model calls a tool on a
validation task or on \emph{simulate}, it almost always calls the right one and no
other. Calling at all is less certain: one model calls the plan validator in $20\%$ of
the trials under the plain prompt and in $93\%$ once a single sentence tells it to. On
\emph{solve} the models call the fitting planner and then add calls, so only
$22$--$39\%$ of the open-weight trials under the plain prompt call it alone.

\emph{RQ3: does the LLM use the tool's output?} Verdicts almost always reach the
answer. Plans are lost in $5$--$13\%$ of the trials in which the planner returned a
valid one. State traces are lost in $70$--$91\%$ of such trials by the open-weight
models and in at least a third by the Claude models. The main cause in the open-weight
runs is that the tool's result fills the context window, so the final turn is refused
or cut.

Supporting analyses cover the token cost of the tools, reasoning mode, a control for
memorized domains, and an external benchmark, PlanBench. We make the following
contributions:
\begin{itemize}
\item A controlled comparison of the same models with and without sound PDDL tools on
five tasks, graded at the delivered final answer, with four measures of benefit: verdict
errors, state accuracy against trace length, problems solved against hardness, and
plan length.
\item A classification of tool choice with every tool offered, which separates calling
the right tool, calling only the right tool, and calling other tools as well, under two
prompts and two reasoning modes.
\item A measurement of how often a correct tool result fails to reach the final
answer, with loss categories that were registered before the data were read.
\item A pre-registered rerun with full answer storage, the complete prompts, and
supporting analyses of cost, reasoning mode, memorization and an external benchmark.
\end{itemize}

\section{Background and Related Work}
% DRAFT 2026-06-14 (goal 2). Re-derived for our framework.

Automated planning studies how to find a sequence of actions that turns an
initial state into one that satisfies a goal. The Planning Domain Definition Language (PDDL)
\citep{mcdermott1998pddl, fox2003pddl21} is the field's standard formalism, and decades of
research have produced sound, complete solvers such as Fast Downward
\citep{helmert2006fastdownward} and FF \citep{hoffmann2001ff} for classical planning and
ENHSP \citep{scala2016enhsp} for numeric planning, together with plan validators such as
VAL \citep{howey2004val}. These systems are correct by construction: a plan they return
provably reaches the goal, and a verdict they issue is sound. They are, however, brittle to
the formal-modelling step: a domain or problem must be expressed in precise PDDL before
any solver can run. Where a model must reason in the solver's place, numeric domains are the
harder regime: tracking arithmetic effects on continuous fluents adds to the discrete
state-tracking that language models already struggle with.

\subsection{LLMs as Planners and as Plan Checkers}
PlanBench \citep{valmeekam2023planbench} gives a model a planning problem in natural
language, asks it for a plan, and checks the plan with VAL. Prompted this way, even strong
LLMs fall well short of a classical planner. \citet{kambhampati2024llmmodulo} argue from
this evidence that autoregressive LLMs cannot plan or verify their own plans by
themselves, and propose LLM-Modulo frameworks, in which the model works in a loop with
sound external verifiers. Our study tests a simpler arrangement. The model may hand a
single task to a sound tool, and there is no generate-and-verify loop.

Reasoning models raised these scores, at first without closing the gap on larger or
obfuscated problems. On PlanBench's $600$ Blocksworld problems, o1-preview produced a correct plan for
$97.8\%$, but for $52.8\%$ of the obfuscated Mystery Blocksworld problems and $23.6\%$ of
$110$ larger Blocksworld problems \citep{valmeekam2024o1prelim}. The journal version of
that evaluation adds that the gains come with large and unpredictable inference costs, and
that o1 improves further inside a compound system with a sound verifier
\citep{valmeekam2025o1tmlr}. In a later evaluation, \citet{correa2025frontier} give
frontier LLMs the PDDL files of $360$ newly generated tasks from $8$ domains of the IPC
2023 learning track, with two solved examples in the prompt, one attempt per task and no
tools. They check each plan with VAL and report that frontier LLMs now rival
state-of-the-art planners, and they replace every name with a random string to control
for memorization.

Other benchmarks split planning into the judgments a planner makes along the way.
ACPBench \citep{kokel2025acpbench} generates boolean and multiple-choice questions from
PDDL for seven such tasks over $13$ domains, so every answer is provably correct. Two of
its tasks are close to ours. Progression asks how an action changes the state, which our
\emph{simulate} task asks for every step of a plan. Validation asks whether an action
sequence is a valid plan, as \emph{validate\_plan} does. With chain-of-thought prompting
and two examples, GPT-4o scored $52.5\%$ on the multiple-choice validation questions, its
lowest task. ACPBench Hard \citep{kokel2026acpbenchhard} asks open-ended versions of the
same tasks, scores each with a symbolic validator, and finds that with few exceptions
every tested model stays below $65\%$. In both benchmarks the model answers without tools.

A related line asks whether a model can check plans itself. With GPT-4 as both plan
generator and plan verifier on Blocksworld, the verifier accepted $38$ of $45$ invalid
plans, and the loop with this verifier solved $55$ of $100$ problems against $88$ with VAL
in its place \citep{valmeekam2023selfcritique}. \citet{stechly2025selfverification} extend
the analysis to three domains, STRIPS planning among them, and find that performance
collapses under self-critique and improves under sound external verification. Outside
planning, \citet{huang2024selfcorrect} report that LLMs struggle to correct their
reasoning without external feedback. Our \emph{validate\_plan} task asks the question
these studies ask, whether a given plan is valid. The difference is that the model may
pass the plan to a sound validator, and we record whether it does.

\subsection{LLMs as Planning Formalizers}
A second line uses the LLM as a formalizer. The model translates natural language into a
formal model, and a sound solver does the search. LLM+P \citep{liu2023llmp} pipelines an
LLM into a classical planner, and \citet{guan2023world} use LLMs to build world models for
model-based planning. Plansformer \citep{pallagani2022plansformer} fine-tunes a model for
plan generation, and \citet{silver2024generalized} apply pretrained LLMs to generalized
planning in PDDL domains. The survey by \citet{tantakoun2025survey} treats LLMs as tools
that write and refine planning models for off-the-shelf planners, and notes that
end-to-end planning by an LLM still lacks soundness guarantees.

\citet{huang2025limit} measure the limits of this approach with zero-shot prompting and no
tools. Models are largely robust to lexical perturbation of domain symbols, and
formalization degrades as the descriptions become more natural. On their obfuscated
Mystery Blocksworld, GPT-4o as a formalizer produced $70$ of $100$ correct plans against
$0$ of $100$ as a planner, graded with VAL. The advantage is not universal. o3-mini scored
$74$ of $100$ as a planner on the same data, and the authors describe the results as
mixed across models. Their work is the published starting point for our PlanBench
section, where we repeat the rescue result and add the control it was missing
(Section~\ref{sec:planbench}).

Two further results bear on how such pipelines are graded. Planetarium
\citep{zuo2025planetarium} checks generated PDDL problems for semantic equivalence with
the intended task. Zero-shot, $96.1\%$ of GPT-4o's problem files parse and $94.4\%$ are
solvable, yet only $24.8\%$ are correct, so solvability alone is a weak check on a
generated model. LLMFP \citep{hao2025llmfp} formalizes planning problems as optimization
problems for an SMT solver instead of PDDL. On Blocksworld and Mystery Blocksworld ($602$
queries each) it reaches optimal rates of $96.2\%$ and $77.7\%$ with GPT-4o, where direct
planning with the same model reaches $41.5\%$ and $0.8\%$.

Agentic systems wrap the solver in a loop. In the system of \citet{lamalfa2026endtoend},
an orchestrator LLM writes the PDDL domain and problem, agents refine them, and the
validated files are passed to an external planner. With GPT-5-mini it raises the average
PlanBench success rate from $76.6\%$ to $91.6\%$ over three runs of $50$ problems per
task, with GPT-5-mini as the judge of success. \citet{gobel2026agentic} expose a step-wise
PDDL simulator to Claude Haiku~4.5 over MCP and let the model choose one action at a time
until a plan validator accepts the plan. On $102$ IPC Blocksworld instances this agentic
setup solves $66.7\%$ against $63.7\%$ for direct planning, at $5.7$ times the token cost
per solution. Their tool set contains no planner, so the model does the search itself.

\subsection{Tool Use and the Decision to Call}
Equipping LLMs with external tools is now standard, from learned tool invocation
\citep{schick2023toolformer} to large API repertoires \citep{qin2024toolllm}. The Model
Context Protocol \citep[MCP;][]{anthropic2024mcp} standardizes how tools are described to
a model and how its calls are relayed, and it is how we expose planners and validators.
BFCL checks a model's calls against the expected function and arguments with an
abstract-syntax-tree method \citep{bfcl2025}, and $\tau$-bench measures multi-turn
tool-agent-user interaction \citep{yao2024taubench}. Benchmarks built on live MCP servers
extend this to many tools and long tasks. They score runs with execution-based evaluators
\citep{luo2025mcpuniverse} or with rule-based checks and an LLM judge
\citep{wang2026mcpbench, guo2025mcpagentbench}, and MCPAgentBench adds distractor tools to
test selection \citep{liu2025mcpagentbench}.

Fewer studies ask whether the model decides to call at all. BFCL separates items where a
call is expected from items where none is \citep{bfcl2025}. MetaTool
\citep{huang2024metatool} asks the model directly whether a query needs a tool and finds
that most models lack this awareness. When2Call \citep{ross2025when2call} poses a four-way
choice that includes a tool call, and builds its items so that answering directly is
always a hallucination. SMART \citep{qian2025smart} studies the opposite error, calling
tools for questions the model could answer from its own knowledge. In each of these the
right decision is fixed when the item is built. In our tasks a sound tool is always
relevant, but the model can often answer correctly without it. Whether it calls the tool
is a behavior we observe, and its cost is measured in the final answer.

A parallel line raises tool use through scaffolding, interleaving reasoning with tool
actions \citep{yao2023react} or offloading numeric subproblems to executable programs
\citep{chen2023pot}. HAL \citep{kapoor2026hal} evaluates agents across models and
scaffolds and reports accuracy against dollar and token cost. Our cost-of-pass analysis
follows that practice. Our setting is at the simple end of this range. Each task has one
relevant tool, and that tool is sound, so the closest analog is single-call function
selection.

\subsection{Positioning}
The planner and verifier studies above, the frontier comparison of
\citet{correa2025frontier} among them, measure what a model does alone. The formalizer
pipelines and the system of \citet{lamalfa2026endtoend} measure what a model achieves
together with a solver, and the call to the solver is part of the pipeline.
\citet{gobel2026agentic} give the model simulator tools but no planner, and a run ends
when the validator accepts a plan. In each of these designs, either the model works
without tools or the call is built into the system, so how often a model calls a sound
tool that it is free to skip is not measured. The tool-calling benchmarks do measure that
decision, on items where the right choice is fixed in advance, and they score the
decision itself.

This paper measures two quantities on PDDL tasks with sound planning tools. The first is
how often a model calls the tool, both when the tool is merely available and when one
sentence asks for it. The second is how often a correct tool result reaches the model's
final answer, which a deterministic checker grades. We know of no earlier study that
reports the two separately for planning tasks. The closest is a preliminary study of an
earlier version of this tool suite \citep{benyamin2025copilot}, which folded both into
one success rate (Section~\ref{sec:prelim}). Our main tasks hand the model complete PDDL
files, so they do not test whether the model can write PDDL. We test that step on
PlanBench \citep{valmeekam2023planbench}, where the prompts are plain English and the
model must write the PDDL before it can call a planner. That section re-measures the
no-tools baseline against the published figures and compares the tools with a control
that keeps the same prompt and removes only the tools (Section~\ref{sec:planbench}).

\subsection{Relation to the Preliminary Study}
\label{sec:prelim}
\citet{benyamin2025copilot} introduced the Planning Copilot, which exposes planners, a
plan validator and a plan simulator to an LLM over MCP. They tested three open-weight
models (Qwen3 at 0.6B and 4B, and GPT-OSS-20B) with and without these tools on the five
task types studied here. With tools, the success rate rose in $14$ of the $15$
model-task cells. On \emph{solve} it went from $0.04$ to $0.78$ for Qwen3-4B and from
$0.28$ to $0.78$ for GPT-OSS-20B, and no model simulated a plan correctly without tools.
The evaluation was preliminary. It used $250$ single-task queries in all, reported the
better of each model's thinking and non-thinking runs, gave no confidence intervals, and
had no control for memorized domains. Its tool-arm system prompt told the model that
calling tools was its only way to solve a task, and a tool-arm trial counted as a success
only if the model had called the correct tool and its final answer was right. Calling and
delivery were therefore folded into one number. The present paper grades $273{,}600$
open-weight trials over two corpora, with confidence intervals and an anonymized-domain
control, and adds a pre-registered study. It confirms the main direction. Tools raise the
rate of correct delivered plans by $51.7$ to $71.0$ points for the three open models of
the pre-registered study, and frontier models go from $22$--$29\%$ unaided to $95\%$ with
the planner. Unaided simulation is again
close to zero ($0$ of $3{,}000$ answers in the exact format under the shared output
budget), but with the budget and format relaxed, models from 4B up get $22$ to $40\%$ of
trajectories right. The paper changes the reading in two places. First, a model may skip a
tool that is merely available. Gemma-MoE-26B called the plan validator in $21\%$ of
\emph{validate\_plan} trials, against $94\%$ when one sentence in the user turn asked it
to. Having the tool available did not lower its delivered accuracy ($89.2\%$ against
$88.3\%$ unaided; difference $+0.9$ points, 95\% CI $[-1.2, 2.9]$). Second, a correct tool
result does not always reach the final answer. On \emph{simulate} the trajectory returned
by the tool left the model no room to answer in $42.7$ to $53.0\%$ of tool-arm trials, and
Gemma-MoE-26B's delivered score with tools fell $15.7$ points below its unaided score
(95\% CI $[-24.7, -6.7]$).

\section{Methodology}
We ask a single, deliberately narrow question: \emph{when a sound symbolic
planner or validator is available as a callable tool, how much does it improve a
language model's performance on individual PDDL tasks, and at what token cost?}
The study crosses five PDDL tasks, five open-weight models, two reasoning modes,
and three experimental arms, and grades every response strictly against a
deterministic solver/validator oracle rather than by self-report.

\subsection{Experimental Pipeline}
A single evaluation harness turns the fixture corpus into graded trials, and every
(model, reasoning mode, arm) cell runs the same four stages. In \emph{setup}, the
harness loads the PDDL domain corpus and connects to the symbolic tools over the
Model Context Protocol \citep{anthropic2024mcp}. In the \emph{oracle} stage, before
any model is queried, an oracle calls those tools directly on every fixture to
produce ground truth (a reference plan, a validity verdict, or a state trajectory,
according to the task); a startup check re-confirms each fixture against its
committed label and aborts the run on any drift. During \emph{trials}, for each
task, paraphrase, and instance the harness builds the prompt, serves the model with
vLLM at temperature~0, and in the tool arms lets it issue up to ten tool calls
before it commits a final answer, logging that answer with its token counts and any
tool calls. Finally, \emph{grading} scores each response strictly against the oracle
(Table~\ref{tab:tasks}), tags it by failure mode, and aggregates it into a success
rate with a Wilson \citep{wilson1927} score interval. The rest of this section
details each stage: the tool suite the model calls, the tasks and fixtures, model
serving, the three arms, and the statistics.

\subsection{The Tool Suite}
The tools the model may call are a suite of sound symbolic planners and
validators, each exposed as a Model Context Protocol \citep{anthropic2024mcp}
function with a typed argument schema and reached through a single
natural-language entry point: the model reads a task description, selects a tool,
emits a structured call, and receives the tool's result. Every tool trial, open-weight or frontier, exposes the same seven tools from two
plugins. The solver plugin provides a classical planner (Fast Downward
\citep{helmert2006fastdownward}), a numeric planner (ENHSP \citep{scala2016enhsp}) and
a tool that saves a plan to a file. The validator plugin provides
\texttt{validate\_domain}, \texttt{validate\_problem} and \texttt{validate\_plan}, which
return a VALID or INVALID verdict, and \texttt{get\_state\_transition}, which returns
the state trajectory a plan induces. The four validator tools run \texttt{pyval} (the
\texttt{pddl-pyvalidator} package), a Python plan validator built on the
\texttt{unified-planning} library, and both planners are also called through
\texttt{unified-planning}. Each task has one matching tool. On \emph{solve} there are
two, and the model picks the planner that fits the domain. The harness never narrows
the list, so every tool trial also tests whether the model picks the right tool, and
calls to the wrong tool do occur. The validator tools take an optional
\texttt{verbose} flag, which the harness removes from the schema the model sees and
fixes to false. The tools accept PDDL either as text or as a file path. The harness
gives no paths, so the model has to copy the PDDL text from its prompt into the call.
In the canonical corpus every call that carried a domain argument passed that text.
The tools are deterministic, and what the model contributes is choosing the matching
tool and passing the task's files into it intact. The
suite packages the Planning Copilot tools of \citet{benyamin2025copilot}, whose
evaluation covered the same five task types with $250$ single-task queries in
total ($10$ problems, $5$ prompt variants, $5$ request types); the corpus graded
here runs $4{,}560$ trials in every model-mode-arm cell, about $18$ times that
entire suite per cell. The
verbatim per-task prompts that expose these tools, together with the one-sentence
steering directive, appear in Listing~\ref{lst:prompts}.

\subsection{Tasks, Oracle, and Fixtures}
Each model is given five PDDL tasks, one tool-relevant per task: \emph{solve}
(find a plan reaching the goal), \emph{validate\_domain} and
\emph{validate\_problem} (judge whether a domain or problem file is well formed),
\emph{validate\_plan} (judge whether a given plan is correct), and
\emph{simulate} (produce the full state trajectory a plan induces, action by
action). Before any model is run, an oracle makes the answer key by calling the same tools on
the original files. On the three verdict tasks the key is \texttt{pyval}'s verdict. On
\emph{simulate} it is the trajectory that \texttt{get\_state\_transition} returns for
the planner's plan. \emph{Solve} has no key plan, and a returned plan counts if
\texttt{pyval} accepts it for the original domain and problem. On the verdict tasks
and \emph{simulate} the checker is the tool, so the tool-verified outcome (defined
under Metrics) is correct by construction whenever the model calls the matching tool
on the unchanged task files. On every task a trial with no call fails at that layer by
construction. That layer therefore measures whether the model calls the right tool
with intact arguments, and it does not measure the tools' own accuracy. On
\emph{solve} the tool and the checker are different programs. Fast Downward or ENHSP
finds the plan and \texttt{pyval} checks it, although both read the PDDL through the
parser of \texttt{unified-planning}. On the other four tasks the tool and the answer
key are the same program, so a fault in \texttt{pyval} would go unseen on the tool
side and would count against an unaided answer that disagreed with it. We therefore
checked the plan side of the answer key with an outside validator, VAL
\citep{howey2004val}. VAL agrees with \texttt{pyval} on $1{,}731$ of $1{,}732$ plans
($99.94\%$, Wilson 95\% interval $[99.67, 99.99]$): all $1{,}000$ \emph{validate\_plan}
test plans and $731$ of the $732$ distinct \emph{solve} plans graded in the delivered
rerun. In the one disagreement \texttt{pyval} accepts \texttt{pick-up} for the action
\texttt{pick\_up}. A second check covers the $745$ \emph{solve} plans of the two Claude
models that both validators could read. VAL agrees on $734$ ($98.52\%$, $[97.38,
99.17]$), and on all $219$ plans of the tool arm. All $11$ disagreements are one fault
of \texttt{pyval}. When an unaided answer writes an upper-case name exactly as the test
file declares it, \texttt{pyval} rejects the plan, although PDDL names are
case-insensitive. This fault lowers a few unaided \emph{solve} grades. It also fails
some tool calls in which the model rewrote a plan with the file's capitals before
passing it to \texttt{validate\_plan} or \texttt{get\_state\_transition}. We report the
grades as stored and give the VAL grades beside them, labelled post hoc. VAL does not
confirm the rest of the key. On the domain and problem files it agrees with the labels
on only $184$ of $238$ ($77.3\%$). Every miss is an invalid file that VAL accepts,
because VAL ignores text after the \texttt{define} form and reads a missing goal as an
empty one. Those labels rest on a strict reading of the PDDL grammar. The
\emph{simulate} trajectories were not checked with VAL.
Grading is end-to-end and strict (Table~\ref{tab:tasks}): a \emph{solve} answer counts
only if \texttt{pyval} accepts the returned plan; a \emph{simulate} answer counts
only if its entire trajectory equals the oracle's under a canonical normal form
(sorted, case-folded, with the boolean/numeric fluent shapes unified), with no
partial credit and no free-text fallback. Both arms are graded on the model's own
final message, by the same parser; a tool arm's trial is \emph{additionally}
scored at a diagnostic layer from the tool's returned result on the model's
arguments, which attests correct selection and faithful invocation. The Metrics
subsection defines the two layers and fixes the delivered answer as the primary
surface (models essentially never contradict the tool, so where the layers
disagree the cause is an answer that never restated the result, not one that
misreported it).

magnitude in scale (0.8B--35B) and two families: Qwen3.5-0.8B, Qwen3.5-4B, Qwen3.5-9B,
a Gemma mixture-of-experts model ($\approx$26B total / $\approx$4B active
parameters, ``Gemma-MoE-26B''), and Qwen3.6-35B.\footnote{Hugging Face checkpoints:
\texttt{Qwen/Qwen3.5-0.8B}, \texttt{Qwen/Qwen3.5-4B}, and
\texttt{Qwen/Qwen3.5-9B}, served in 16-bit precision; the two
mixture-of-experts checkpoints, \texttt{cyankiwi/gemma-4-26B-A4B-it-AWQ-4bit}
and \texttt{cyankiwi/Qwen3.6-35B-A3B-AWQ-4bit}, are community AWQ-INT4

from the three larger models ($\geq$9B: Qwen3.5-9B, Gemma-MoE-26B,

PyTorch~2.11.0, CUDA~13.0 runtime, executed with Apptainer~1.4.5), one model per

caching enabled; each job is allocated one GPU, six CPU cores and 48\,GB of host
memory on compute nodes running Rocky Linux~9.7 (kernel 5.14.0-611, NVIDIA driver
595.58.03).\footnote{Serving-version provenance, read from the vLLM start-up banner

temperature~0 removes.
The context window is 16{,}384 tokens; per-task decode caps are 8{,}192 tokens for

tool calls. In practice tool use is overwhelmingly single-shot: across the $91{,}200$
with-tools trials the median trial issues one call, and $60\%$ issue exactly one (of
which $90\%$ succeed). The $27\%$ that issue two or more are retries after an
unsuccessful call, and their success rate falls monotonically as call count rises
($67\%$ at two calls to ${\approx}25\%$ beyond five). A further $13\%$ issue no call at

therefore remove low-yield retries rather than successes. The reasoning mode is toggled per run (\emph{think}~=~on/off via the

reasoning trace and the final answer share the \emph{same} per-task decode cap, a
shared budget that drives the confound we treat explicitly below. Tools are
exposed to the model through the Model Context Protocol \citep{anthropic2024mcp}
as standard function definitions; system prompts are thin per-task policy stubs,
with all argument schemas carried by the tool definitions rather than the prompt.

\subsection{The Three-Arm Design}
Every (model, mode, task) is run in three primary arms (a fourth, control arm
follows); arms are scored separately and never pooled, and every comparison is
between two arms of the \emph{same} cell:
\begin{itemize}
\item \textbf{no-tools}: the model answers from parametric knowledge. The PDDL
tools are removed and the answer format is requested in the system prompt alone: a
JSON answer on \emph{solve} and \emph{simulate}, a closing verdict line on the three
validation tasks. Per-task JSON-schema-constrained decoding was intended for this arm
but did not take effect, so no decoder-level constraint was active and an unaided
failure can be a failure of format as well as of content (Limitations).
\item \textbf{tool-available (plain)}: the \emph{byte-identical} neutral task
prompt, now with the tools exposed. (The thin per-task system prompts are structural
mirrors sharing the same role-framing first sentence and sentence count. They differ
in their policy clause, ``use the available tool'' vs.\ ``use your own reasoning,''
the latter adding an output-format reminder on the verdict tasks; we revisit this
small instruction-surface difference in Limitations.) Differencing this arm
against no-tools yields the \emph{availability gap}, which isolates tool presence.
\item \textbf{tool-steered}: the neutral prompt plus exactly one appended
sentence directing the model to use the tool. Differencing against the plain arm
yields the \emph{steering gap}.
\end{itemize}

no-tools and tool-available \emph{validate\_plan} system prompts (representative;

The two contrasts map onto the function-calling literature: the plain arm
measures \emph{relevance detection} (does the model spontaneously invoke the
right tool when its existence is known but not urged?) and the steered arm
measures \emph{function selection} (told to use a tool, does it pick the correct
one?) in the sense of the Berkeley Function-Calling Leaderboard
\citep{bfcl2025}. Because the per-task tool split enforces each tool's required
arguments through its schema, argument-filling errors are largely structural, so
the steered contrast isolates selection rather than parameter construction.
A fourth, \emph{control} arm (the steering directive with the tools still
removed) tests whether the directive alone moves the no-tools floor. It serves
only as a control: its result is reported beside the steering finding (Results,
Table~\ref{tab:ster-units}), and its design and full tables are in the Technical
Appendix. The \emph{realizable benefit} of
the tool, used as the cross-mode spine below, is success(tool-steered)
$-$ success(no-tools): what a deployment that actually prompts for tool use would
realize.

\subsection{Metrics, Confidence Intervals, and Signed Significance}
\paragraph{One primary surface, two layers.} The primary outcome on every task,
in every arm, is the \emph{delivered} success rate: the answer in the model's own
final message is graded against the deterministic oracle, by the same parser in
both arms. This is the surface a user of the system experiences; a correct result
that the model obtained from a tool but never carried into its answer does not
count. In the tool arms we grade each trial at a second, diagnostic layer as
well: \emph{tool-verified} success asks whether a correct result appeared in some
tool response during the trial, whatever the final message then said. The two
layers separate the mechanism (did the model drive the tool to a correct
result?) from the outcome (did that result reach the answer?), and their
difference is itself a measurement, the \emph{delivery gap}. Tool-verified
numbers are never headlines; wherever one appears below it is labeled as the
mechanism layer. One boundary case gets its own outcome category: a trial whose
final message is empty although a correct tool result exists earlier in the
transcript is \emph{delegation-terminal}. The strict rule grades it as a
failure, since the answer never reached the user; crediting such trials instead
would move $3.6\%$ of tool-arm rows and flips no headline verdict.

\paragraph{One surface, three value shapes.} Our corpora differ in how much of
the final message was stored, and the reported value shape is set by the storage,
while the estimand is the same throughout. Where the full text is available the delivered rate is an
exact point with a Wilson 95\% interval, written $[a,\,b]$. Where responses were
stored as truncated snapshots, a snapshot that ends before any verdict is
visible leaves the trial \emph{indeterminate}: it cannot be graded correct or
incorrect. Cells containing indeterminate trials are reported as censoring
bounds, written \cbnd{a}{b}: the delivered rate lies between ``every
indeterminate trial failed'' ($a$) and ``every indeterminate trial succeeded''
($b$). The two notations are typographically distinct on purpose and are never
mixed in one cell. A claim that involves a bounded cell is asserted only if it
survives the claim-adverse end of every bound involved (with the Wilson interval
then placed on that end), and cells where the indeterminate mass could flip the
call are stated as \emph{undecided} rather than resolved. This heterogeneity of
shapes is itself evidence about protocol design: full-response storage buys
exactness, and Results opens with a table saying which corpus bought it.

In the tool arms we additionally record \emph{tool\_selected} (whether the model
called the task-matching tool at all); tool calls and their results are stored
in full in every corpus, so invocation rates and tool-verified rates are exact
everywhere, whatever the final-answer storage. Failures are typed
(tool not selected, wrong tool, verdict mismatch, unparseable output, trajectory
mismatch), with cap-truncated responses re-tagged as truncations rather than
being counted as content failures. A Wilson 95\% score interval
\citep{wilson1927} is computed for every reported proportion, and \emph{arms are never pooled}: each statistic comes from
exactly one (model, mode, arm) corpus, and only differences \emph{between} such
statistics are formed. Because each instance is scored under three paraphrases,
trials within an instance are not independent: the intraclass correlation is
$\approx$0.6 and the design effect $\approx$2.2--2.7, so the effective sample size is
roughly half the nominal count and these Wilson intervals are correspondingly
anti-conservative. We verified that every headline verdict ($+50$--$92$\,pp, and the
smallest reported gaps) remains CI-disjoint after inflating intervals by
$\sqrt{2.7}$, and flag the one verdict-relevant gap that does not (the $-5$\,pp
\emph{validate\_problem} steering dip) individually. As a robustness check on the largest
verdict-relevant contrast, we additionally fit an instance-level random-intercept logistic model to
the Gemma-MoE \emph{validate\_plan} plain-vs-steered comparison (success $0.206\!\to\!0.926$); the
steering effect is strongly favorable and significant (log-odds $+7.5$, posterior SD $0.10$; a
population-averaged GEE with an exchangeable working correlation clustered on instance agrees), so
the verdict is invariant to whether non-independence is handled by design-effect inflation or by an
explicit random-effects model. We do not fit such models cell-by-cell because many cells are
near-degenerate or completely separated (the \emph{simulate} no-tools baseline is $0/3{,}000$
format-exact on the canonical (shared-budget) corpus,
and the tool arms reach $P(\text{correct}\mid\text{call})\!\approx\!0.99$), where a
maximum-likelihood GLMM is undefined or unstable, whereas the design-effect inflation never fits a
per-cell model and so remains valid at the boundary; with cluster size three the random-effect
variance is also only weakly identified.

Verdicts use a \emph{signed} significance rule. A per-model gap counts as
favorable evidence only when the two arms' 95\% intervals are disjoint
\emph{and} the gap points the hypothesized way (the tool helps); a disjoint gap
pointing the other way is tallied separately as significant-\emph{against}, which
we treat as a finding in its own right. This sign-awareness matters: on \emph{validate\_plan} mere tool
availability collapses one $\geq$9B model's validator invocation to $21\%$ of
trials, a mechanism-layer drop of $-67$\,pp in tool-verified success, and a
sign-blind disjointness test would credit that highly significant movement as
the tool ``having an effect.'' The signed rule reads it as evidence against. Requiring disjoint 95\% intervals is deliberately
conservative: it controls the false-positive rate well below $\alpha=0.05$, at
the cost of power on small gaps, so a \textsc{no} verdict means ``no movement we
are willing to call significant,'' not ``no movement.'' We do not apply a separate family-wise
correction across cells, but the headline verdicts are not thereby exposed to
multiplicity. The design-effect inflation already widens every interval by
$\sqrt{2.7}$, so a gap is called significant only when its arms are disjoint at an
effective $z\approx3.2$ rather than the nominal $1.96$; that threshold is already
stricter than a Bonferroni bound for a confirmatory family as large as ${\sim}30$
contrasts (Bonferroni $z\approx3.1$), so the verdicts clear simultaneous control
without a dedicated correction. The reported effects are moreover large, and we
treat the few borderline gaps as exploratory rather than confirmatory.

\subsection{Cross-Mode Aggregation and the Robust Floor}
\emph{think}~=~off is the clean headline: the model answers directly, so the
availability and steering gaps measure the tool, unconfounded. Under
\emph{think}~=~on the shared decode budget truncates a large fraction of $\geq$9B
no-tools trials (the baseline uses up its decode budget on reasoning), so raw
\emph{think}~=~on gaps conflate the tool's value with baseline budget collapse.
We therefore make cross-mode claims only through budget-insensitive statistics.
The spine is the realizable benefit (steered, not plain: under
\emph{think}~=~on the plain arm largely stops calling the tool, so its
availability gap also includes a mode-dependent tool-calling failure that
steering repairs). Gaps carry Newcombe MOVER intervals \citep{newcombe1998}, and the mode difference
$\Delta(\mathrm{on}-\mathrm{off})$ carries a MOVER interval for the difference of two
independent gaps, valid because the two reasoning-mode corpora share no
trials. The \emph{robust floor} is the minimum realizable benefit over the two
reasoning modes (the smaller of the two mode point estimates, a deliberately
conservative construction): a lower bound that neither mode's decode budget can inflate.
Against a deliberately conservative $+30$\,pp threshold this sorts the tasks into
\emph{robust} (every $\geq$9B floor $\geq +30$\,pp), \emph{sole-source} (baseline at
$0$ in both modes, where a benefit with no baseline cannot be budget-confounded), and
\emph{budget-dependent} (some floor below $+30$\,pp, where the large
\emph{think}~=~on stretch is the artifact).

\subsection{Contamination Control}
Because the domains are public, an unaided baseline could be inflated by
memorization. A separate sweep re-ran the entire matrix on structurally identical
domains with every surface symbol (the names of the domain and of its types,
predicates, functions, actions, constants and objects) renamed to words from an
unrelated theme. The renaming is lexical: action arities and the precondition and
effect structure are unchanged, so the probe tests memorization of names, not of
structure. We pair the two corpora trial by trial and count a difference as negligible
when its $90\%$ interval, clustered by domain or by problem (whichever is wider), lies
inside $\pm5$\,pp, a test chosen after the sweep. Under \emph{think}~=~off this
criterion is met for every model pooled over the five tasks, and no headline per-task
interval admits a canonical advantage of $5$\,pp or more (Results), so the data rule
out a memorization advantage of that size on the baseline the availability gap is
measured from. Under \emph{think}~=~on the criterion is not met for three Qwen models,
with the renamed corpus lower. There the clearest cell traces to tokenization rather
than memory: the renamed prompts ran $\approx$5\% longer,
so more trials truncated under the shared budget while success-given-completion
was unchanged. This is itself a live demonstration of the budget confound the
cross-mode analysis controls for.

\section{Results}
This section answers the three research questions in turn. The analyses that
predate them, which cover the main sweep task by task together with cost, reasoning
mode and contamination, follow in Section~\ref{sec:supporting}.

We organize the evaluation around three research questions.
\begin{enumerate}
\item[\textbf{RQ1.}] Do PDDL tools help an LLM do planning-related tasks? We compare
the same model with and without the tools on four measures: the false positives and
false negatives of its plan verdicts (\emph{validate\_plan}); the share of simulated
states that are correct, as a function of the length of the simulation
(\emph{simulate}); the share of problems solved, as a function of how hard the problem
is (\emph{solve}); and the length of the plans it delivers (\emph{solve}).
\item[\textbf{RQ2.}] Does the LLM know to choose the right PDDL tool? Every tool is
offered, and we report the share of trials that call exactly the right tool and no
other, the share that call the right tool at all, and the share that call other tools
as well.
\item[\textbf{RQ3.}] Does the LLM know how to use the tool's output? We report the
share of trials in which the tool returned the right result and the model's final
answer was still wrong.
\end{enumerate}

\paragraph{State traces against trace length.} Our \emph{simulate} grader is
all-or-nothing: a trace counts only if every state equals the oracle's. To see how
correctness changes with length we also score each answer state by state, as the share
of the oracle's states that the answer reproduces at the same position, where a state
is the set of true predicates together with the numeric values. Many answers are cut
off before the trace ends. They are then unreadable as JSON, and they score zero on
both measures. A third, lenient score also reads the complete leading steps of such an
answer. It is more forgiving than our grader, and we report it only beside the strict
score. Six of the $100$ problems are left out here because the plan shown in the
prompt was not the plan that the oracle trace belongs to, which leaves $94$.

State accuracy falls with trace length in every model and arm
(Figure~\ref{fig:rq1-simulate}; $\rho$ between $-0.23$ and $-0.73$ across the thirteen
cells of Table~\ref{tab:rq1-simulate}). Beyond $40$ actions, ten of the thirteen cells
contain no exact trace, and the best cell reaches $10\%$. Averaged over lengths, the
tools raise the share of exact traces for both Qwen models and both Claude models, for
example from $18.8\%$ to $30.1\%$ for Qwen3.6-35B and from $35.1\%$ to $51.1\%$ for
Sonnet, with overlapping intervals in each case. For Gemma-MoE-26B the tools lower it,
from $25.5\%$ to $8.9\%$. The tool arms fail mostly by delivering no readable trace
($238$ of Gemma's $282$ plain-arm answers), a loss that RQ3 examines. The lenient
score changes one reading. Sonnet's unaided strict score is $36.7\%$ and its lenient
score is $77.7\%$, above the $59.8\%$ of its tool arm: most of its unaided failures are
traces that are right as far as they go and end early. Both Claude figures are lower
bounds where storage cut the answer.

\subsection{RQ2: Does the Model Choose the Right Tool?}
\label{sec:rq2}
% Every number in this subsection is generated: tools/reanalysis/rq23_metrics.py
% (development/NUMBERS.md, block "RQ2 metrics"); table rows by tools/reanalysis/rq23_tex.py.
Every with-tools trial offers all seven tools. We sort each trial by the set of tools
it called: no tool; only the right tool; the right tool and at least one other; other
tools only. The right tool is the task's validator on the three validation tasks, the
state-transition tool on \emph{simulate}, and on \emph{solve} the planner that fits the
domain (the classical planner on a classical domain, the numeric planner on a numeric
one). On \emph{solve} this is stricter than the invocation rate used elsewhere in this
paper, which accepts either planner. The classification reads the stored tool calls,
which every corpus kept in full, so this question can use the main sweep as well as
the rerun and the frontier runs. The three corpora are never pooled. Like the measures
of RQ1, the classification was defined after the data were collected.

Two regime vocabularies appear below and should not be conflated. A \emph{task} axis
sorts the five tasks by their unaided baseline: \emph{sole-source} (essentially
no unaided success as deployed), \emph{headroom} (a weak but improvable baseline), and \emph{mixed}
(availability can hurt). A separate \emph{cross-mode} axis (Robustness) sorts tasks
by whether the realizable benefit survives reasoning mode: \emph{robust},
\emph{budget-dependent}, and again \emph{sole-source}. The two axes share only the
word sole-source (a task with no baseline is sole-source either way) and are
otherwise independent.

\subsection{Two Tasks the Model Cannot Do Unaided}
\emph{Solve} and \emph{simulate} are sole-source on the baseline side: unaided,
they essentially do not happen (Figure~\ref{fig:solesource}). Unaided
\emph{solve} is floored at $8$--$11\%$ across the $\geq$9B models, exactly
measured. What the tool delivers back is cleanest at the frontier tier, where
storage permits exact delivered rates: Claude Haiku 4.5 rises
$22\!\to\!95\%$ and Claude Sonnet 4.6 $29\!\to\!95\%$, both CI-disjoint, both
sitting exactly $5.0$\,pp under their own mechanism layer of $100\%$ (the
delivery-gap analysis below takes up those five points). On the open-weight
roster the tool arm's delivered rates are censoring bounds: the 9B's
\cbnd{26.0}{58.7} clears its $10.7\%$ baseline even if every censored trial
failed, though by under a point once the clustering correction is applied, so we
read it as exploratory; Gemma (\cbnd{14.3}{35.3}) and the 35B
(\cbnd{12.7}{53.7}) straddle and stay undecided. The mechanism layer points to invocation as the reason the
open-roster bounds sit so far under their tool-verified rates of $63$--$99\%$. Where the plain arm leaves headroom (Qwen3.6-35B invokes the
planner on only $68\%$ of trials) steering raises invocation
to $94\%$, and every $\geq$9B model is $\geq$93\%
accurate when it does call the planner, so what limits the tool path on
\emph{solve} is the invocation rate.

\emph{Simulate} is more extreme: unaided \emph{format-exact} success is $0\%$ for
every open-weight model, in both
reasoning modes, across all $3{,}000$ trials (a rule-of-three $95\%$ upper bound of
$\leq$0.1\%). The tool runs the simulation correctly at the mechanism layer on
$65$--$92\%$ of plain-arm trials ($83$--$97\%$ steered), but almost none of that
reaches the delivered answer on this corpus: not one open-roster tool-arm trial
yields a determinate delivered success, and the bounds top out at
\cbnd{0}{20}--\cbnd{0}{39} for the $\geq$9B models. The determinate failure mass
is dominated by trials in which the model drives the tool correctly and then
exhausts its decode budget before restating the trajectory, a with-tools failure
mode in its own right. The unaided zero, meanwhile, is a property of the deployed budget
and format requirements, not an absent capability. Success demands
canonical-form deep-equality of the \emph{entire} state trajectory against the
oracle (structured JSON, no partial credit, no free-text fallback), and the
unaided failures decompose ($\geq$9B) into $68\%$ unparseable trajectory JSON,
$29\%$ truncated at the $6{,}144$-token cap, and only $3\%$ parsed-but-wrong
(Figure~\ref{fig:failtax}): the models fail on format and budget before content is
tested. A budget-decoupled control isolates the content question. Giving the
reasoning trace and the answer separate decode allowances (a two-call continuation
that stops decoding at the think-close tag; \emph{think}=on, Qwen roster, run as a
separate corpus never pooled with the canonical one) and grading with a wrapper-tolerant
two-metric grader, unaided content-correct state tracking rises to $23.0\%$ (4B),
$22.3\%$ (9B), and $40.0\%$ (35B), with the $0.8$B model alone still at $0\%$;
re-grading the main corpus's stored responses under the same tolerant grader
recovers at most $0.7\%$, but those responses are stored as $500$-character snapshots
that are too short to regrade (Technical Appendix), so this figure does not establish
how much of the recovery is due to the budget and how much to the grader.
Format compliance stays $0\%$ for all four models (none ever emits the exact
requested wrapper), so strict content-and-format success remains $0\%$ across the
board. The comparison in the matching mode is therefore
$22$--$40\%$ content-correct unaided against a tool-arm mechanism layer of
$87$--$96\%$; a delivered-surface version of that contrast cannot be computed
from this corpus (the tool arm delivers no determinate trajectory), and the
claim ``these models cannot track state at all'' does not
survive the control.

\subsection{The Delivery Gap: What Reaches the Answer}
The two grading layers let us measure something the tool-use literature usually
cannot see: how much of what the tool computes actually reaches the model's
answer. Table~\ref{tab:deliverygap} (and the top row of Figure~\ref{fig:funnel})
reports both layers for the frontier
with-tools runs, where storage permits exact delivered rates. The pattern is
sharp and identical at both capability tiers. On the three validation tasks the
gap is zero to within a tenth of a point: a verdict is a short string, and the
model that obtains it restates it. On \emph{solve} both models deliver $95.0\%$
against a mechanism layer of $100\%$: a $+5.0$\,pp gap with the same failure
anatomy at both tiers. Every Sonnet failure is a transcription error made while
restating the tool-validated plan into the final answer (five plans, zero
omissions); Haiku's five are three transcription errors and two omissions. On
\emph{simulate} the gap opens to tens of points: the tool runs the trajectory
correctly on $97$--$99\%$ of trials, and the delivered rate is
\cbnd{52}{64} (Haiku) and \cbnd{49}{62} (Sonnet). Half the Sonnet failure mass
is output budget (trajectories cut mid-stream or censored at the cap), the rest
split between answers with no coercible trajectory and wrong state content.

The gap therefore tracks the length of what must be restated: a verdict (words)
loses nothing, a plan (lines) loses five points, a trajectory (full state dumps)
loses a third or more. A stronger model does not close it: Sonnet and Haiku tie
at $95.0$ on \emph{solve} with the same five-failure count, and their
\emph{simulate} bounds overlap almost completely. On this evidence the gap is a
property of answer length interacting with the output budget, not of model
strength. The probe below tests the budget half of that reading directly.

\textbf{Output-budget probe.} Under a pre-registered protocol (Technical
Appendix) we re-ran the same $100$ \emph{simulate} trials per tier with the output
allowance raised from $6{,}144$ to $64{,}000$ tokens and the stored response
enlarged from $16$K to $256$K characters, so that no answer is censored. With the
larger allowance, $16/25$ of the previously truncated, budget-fitting Sonnet
failures became correct, compared with $7/19$ of its other failures re-run under
the same apparatus (one-sided Fisher $p=0.069$); this did not meet the
pre-registered confirmation criterion. Haiku met that criterion, with $12/17$
versus $1/12$ conversions ($p=0.0011$), while none of its $14$ summary-only
failures became correct. Under the 64K output allowance, delivered accuracy with
versus without tools was $70\%$ $[60,\,78]$ versus $44\%$ $[35,\,54]$ for Sonnet
and $65\%$ $[55,\,74]$ versus $58\%$ $[48,\,67]$ for Haiku. Despite the larger
allowance, $30\%$ and $35\%$ of the tool-arm trials still failed, and no
tool-arm final response reached the output-token cap. The probe corpus is
reported on its own; the canonical cells and their censoring bounds
(\cbnd{49}{62}, \cbnd{52}{64}; Table~\ref{tab:deliverygap}) stand unchanged.

The open-weight roster shows the same structure wherever it can be measured. On
the canonical corpus the tool arms' delivered rates are bounds, so the gap is
bounded rather than pointed; the full-storage rerun (Table~\ref{tab:howtoread};
within-corpus contrasts only) makes it exact for open-weight models: \emph{simulate}
delivered reaches only \cbnd{8.3}{10.7} (4B), \cbnd{12.0}{16.7} (9B),
\cbnd{6.0}{20.7} (Gemma), and \cbnd{12.7}{13.7} (35B) against plain-arm
mechanism layers of $63$, $83$, $44$, and $92\%$. The
same corpus also shows the gap can run \emph{backwards}: on Gemma's
\emph{validate\_plan} cell the mechanism layer is $0.9\%$ (the model almost
never completes a valid tool interaction) while the delivered rate is
\cbnd{30.0}{63.1}, because the model answers the verdict question directly, in
prose, without the tool, a case the availability analysis below has to respect.

\subsection{Two Validation Tasks: Headroom and Rescue}
On \emph{validate\_problem} the unaided model is genuinely partly competent: the set
is balanced one-to-one, so a constant ``VALID'' guess scores $\approx$50\%, and the
$\geq$9B models clear that floor before any tool ($65.7$--$75.7\%$, exact). On the
delivered surface the availability picture is favorable where it can be decided
and undecided where it cannot: the 9B rises to \cbnd{92.2}{95.3}, clearing its
baseline even if every censored trial failed; Gemma's \cbnd{84.3}{99.8} clears at
the 95\% level but by too little to survive the paraphrase-clustering correction,
so we flag it as near-threshold; and the 35B's \cbnd{74.7}{97.8} straddles its
$75.7\%$ baseline and stays undecided. No model moves against. \emph{Validate\_domain} behaves
differently. Because its fixtures run $5{:}1$ valid-to-invalid, a constant
``VALID'' already scores $83\%$; yet unaided, every $\geq$9B model lands \emph{at or
below} that trivial line (pooled $26$--$78\%$) and discrimination is unreliable across
the board, from near-chance to only modest (balanced accuracy $53$--$74\%$; Table~\ref{tab:vdom}). Qwen3.5-9B is the clearest
case: it answers
``INVALID'' almost reflexively (true-positive rate $12\%$, true-negative rate
$95\%$), scoring $26\%$ pooled but $53\%$ balanced. Here the tool \emph{rescues} a task the models cannot do reliably.
The delivered lower bounds alone establish it: \cbnd{99.7}{100.0} (9B),
\cbnd{93.3}{98.1} (Gemma), and \cbnd{91.9}{99.2} (35B) against exact unaided
baselines of $26$, $78$, and $68\%$, favorable for all three at the claim-adverse
end and past the $83\%$ trivial line at every lower bound. Balanced accuracy on
the delivered surface tells the same story: the steered arm reaches
\cbnd{100.0}{100.0} (9B), \cbnd{92.2}{95.0} (Gemma), and \cbnd{82.7}{99.2} (35B)
against unaided $53$, $74$, and $65\%$, clearing the baseline at the
claim-adverse end for all three; the 35B's wide bound comes from its
$60$-trial negative arm, of which $19$ are censored (Table~\ref{tab:vdom}). The
\emph{validate\_domain}
verdict holds from 4B up (\cbnd{84.2}{100.0} against $19.2\%$); the 4B's
\emph{validate\_problem} cell is undecided. The 0.8B model moves sharply and
decidedly \emph{against} on both tasks even at the censoring bounds' favorable
end (\emph{validate\_domain} $80.8\!\to\!$\cbnd{43.9}{45.8};
\emph{validate\_problem} $51.2\!\to\!$\cbnd{4.0}{5.8}): small-model
tool-mishandling, in which it calls the right tool but omits required arguments,
costs it answers it could have produced unaided. Steering
does not help either validation task at the mechanism layer
($-5$--${+}1$\,pp); the one
CI-disjoint movement (a $-5$\,pp dip on \emph{validate\_problem} for the 9B)
points mildly against and does not survive the paraphrase-clustering correction
above, so we treat it as non-confirmatory. Once a capable model has the tool it
already calls it, and the nudge matters only where the plain arm under-calls, as in
the next case.

\subsection{When Availability Backfires at the Tool Path, and Steering Repairs It}
\emph{Validate\_plan} is the one task the unaided model already does well
($\geq$9B no-tools $80$--$91\%$, exact), and it is where the two grading layers
tell visibly different stories, so we give both and keep them labeled.

At the mechanism layer the picture is exact. Merely making the
tool available collapses the tool path for two of three $\geq$9B models:
Gemma-MoE-26B's tool-verified rate falls $88\!\to\!21\%$ ($-67$\,pp) and
Qwen3.6-35B's $91\!\to\!82\%$ ($-9$\,pp); only Qwen3.5-9B improves
($80\!\to\!93\%$, $+13$\,pp). The decomposition pins the cause. Writing
tool-path success as $P(\text{call})\times P(\text{correct}\mid\text{call})$,
Gemma's collapse is entirely in the first factor: under the plain prompt it
calls the validator on only $21\%$ of trials, but \emph{when it calls it is
$99\%$ correct}. Steering moves only $P(\text{call})$ (from $21\!\to\!94\%$) and
the mechanism layer follows it almost exactly ($0.94\times0.99=0.93$;
Figure~\ref{fig:mechanism}). Across every $\geq$9B tool
cell except 9B \emph{simulate} ($\approx$81\%), $P(\text{correct}\mid\text{call})$
stays $\geq$92\% and varies little between arms (Table~\ref{tab:decomp}); nearly
all between-arm and between-model variance
at this layer is variance in \emph{whether the model calls}. These rates are
computed from the stored tool transcripts and are exact in every corpus.

On the delivered surface, the canonical corpus cannot decide whether that
collapse hurt the user's answer. All three $\geq$9B tool cells are censored into
straddling bounds (Gemma \cbnd{6.6}{99.6} with $93\%$ of snapshots censored; the
35B \cbnd{55.0}{90.3} against $90.9$; the 9B \cbnd{80.8}{87.2} against $79.7$),
so the availability gap on this task is \emph{undecided} at the primary surface,
in both directions: neither the $-67$\,pp harm nor the $+13$\,pp lift survives as
a delivered claim here. The full-storage rerun says why caution is warranted:
in that corpus Gemma's delivered rate is \cbnd{30.0}{63.1} while its mechanism
layer is $0.9\%$. The model that almost never completes a tool call still
answers the verdict question directly, in prose, and is often right. Not
calling is not the same as not answering, so a collapse of the tool path only
bounds, and does not determine, the collapse of the answer. What survives at
full strength is the invocation finding itself: availability swings whether the
model uses the tool by large, model-specific amounts, and one directive sentence
moves invocation from $21\%$ to $94\%$.

A pre-registered control asks whether that sentence is simply a better prompt.
We appended the same directive to the no-tools prompt, with the tools removed
and the system prompt still stating that they are unavailable, and ran it
beside a neutral-prompt arm in the same job on six (model, mode) units, as a
paired equivalence test at $\pm5$\,pp (Table~\ref{tab:ster-units}, with the
design and full tables in the Technical Appendix). All six pooled units and all
eight eligible task cells met the $\pm5$\,pp equivalence criterion; excluded
task cells remain unresolved. In the matched cell, Gemma-MoE-26B
\emph{validate\_plan} at \emph{think}=off, the sentence worth $+72.0$\,pp at the
mechanism layer with the tool present is worth $+0.63$\,pp on the model's own
answer with it absent ($90\%$ interval $[-0.46,\,+1.73]$). This supports the
interpretation that steering acts through tool use in the matched Gemma cell.

This also explains an apparent size inversion. In the plain arm's mechanism
layer the 9B
``beats'' the 35B (\emph{solve} $99\%$ vs.\ $63\%$; \emph{validate\_plan} $93\%$
vs.\ $82\%$), but this reflects the invocation rate rather than capability: the
tool path tracks invocation almost 1:1, accuracy-given-a-call is $\geq$93\% for both, and
steering closes the gap (35B \emph{solve} $63\!\to\!92\%$ at that layer). The invocation rate even
flips with reasoning mode (under \emph{think}=on the 35B calls the validator on
$99.9\%$ of trials, the 9B on $69\%$). The 35B's unaided baselines exceed the 9B's
on every validation task; the inversion is a behavioral difference in spontaneous
invocation rather than a capability gap. Because our two largest models are AWQ-INT4
while the 9B is 16-bit, we read this cross-model inversion as an invocation-rate
phenomenon we observe rather than a controlled size effect (see Limitations).

\subsection{Does the Advantage Track Difficulty?}
These two difficulty analyses run at the mechanism layer (the tool-arm side of
each bin contrast is tool-verified, since binned delivered rates on the
canonical corpus are bounds too wide to compare), and are labeled accordingly.
An advantage can only be \emph{seen} to change where the no-tools baseline has room
to move, which makes \emph{validate\_plan} the case where this is visible:
as the reference plan lengthens, unaided accuracy degrades
($94\!\to\!91\!\to\!62\%$ over short/medium/long bins) while the tool path holds
($\approx99\!\to\!98\!\to\!89\%$), so the gap widens $+5\!\to\!+7\!\to\!+27$\,pp;
the harder the instance, the more the tool is worth. The other two length-sensitive
tasks bracket this case: \emph{solve}'s gap is large but roughly constant
($+87\!\to\!+87\!\to\!+89$\,pp), both arms pinned (baseline floored, tool near
ceiling); \emph{simulate}'s gap is large but \emph{declines}
($+100\!\to\!+93\!\to\!+77$\,pp, CI-disjoint), because although its baseline stays
floored at a format-exact $0$, the tool arm itself degrades on long trajectories, the one place
tool-assisted success erodes with difficulty. Object count, by contrast, moves
nothing: the \emph{validate\_problem} gap is flat at $+22/{+}23/{+}23$\,pp and the
other tasks are flat too. The tool's advantage tracks plan length
and is flat in object count.

\subsection{What the Tool Costs}
The tool is not free (Figure~\ref{fig:tokens}). Per trial it raises total token
consumption (input~$+$~output, summed over turns) several-fold:
$\approx$4--6$\times$ on the $\geq$9B models, and up to $\approx$15$\times$ for the
smaller 4B. The added cost is \emph{input} rather than output: the unaided model is
output-heavy (input:output $\leq$1:1, as low as $0.3$:1 on \emph{solve}, where it reasons in the open), while the
tool arms are strongly input-heavy ($\approx$6--12:1) because the tool schemas and tool outputs
are re-fed every turn. (Server-side prefix caching, $\approx$90\% on this roster,
makes the re-fed \emph{schemas} cheap to compute, but tool \emph{outputs} are
uncached and the tokens are still real context. Our token totals count these raw, so where
caching applies the tool's reported cost is, if anything, an over-estimate.) A
production system could lower the input overhead further by not re-feeding full tool
outputs on every turn, summarizing or eliding them once consumed; our harness re-feeds
them verbatim, so the cost-of-pass we report is a faithful worst case rather than a
deployment-tuned figure.

Whether it is worth paying depends entirely on the baseline: the choice of
metric flips the verdict by $\approx$10$\times$ on identical data, so we report
\emph{cost-of-pass} $=$ total tokens $\div$ successful trials (lower is better),
which factors exactly as (tokens-per-trial ratio) $\div$ (success-rate ratio).
On this corpus the tool arms' delivered rates are bounds, so these ratios count
successes at the mechanism layer and are labeled tool-path economics; the
delivered-surface cost-of-pass is a range across the bound
(Figure~\ref{fig:tokens}).
Where the baseline is floored the tool pays for itself: on \emph{solve} it is
$\approx$0.3--0.4$\times$ the cost per success (e.g.\ $\approx$4$\times$ more tokens
$\div$ $\approx$9--13$\times$ more correct answers); on the delivered surface the
same ratio is a range, $0.6$--$1.6\times$, because the tool arm's delivered
successes are bounded (Figure~\ref{fig:tokens}). At the frontier, where
delivered \emph{solve} is exact, the verdict inverts: the unaided baseline is no
longer floored ($22$--$29\%$) and the re-fed context dominates, so a delivered
pass costs $3.1\times$ (Sonnet, $18.6$K vs.\ $6.0$K tokens) and $6.1\times$
(Haiku, $48.5$K vs.\ $8.0$K) the unaided tokens, and on \emph{simulate}
$84$--$106$K against $10$--$15$K (Sonnet), a $5$--$11\times$ premium
per delivered trajectory. On \emph{simulate} the
unaided arm produces no format-exact success here, but the tool arm also rarely
delivers its trajectory within budget, so at the delivered level neither arm's
per-success cost is identified on this corpus and we make no \emph{simulate}
cost claim beyond the mechanism layer. Where
the baseline is already strong the tool is a luxury: $\approx$3--5$\times$ costlier
per success on most \emph{validate\_*} cells ($\geq$9B), where it is only modestly
more often right and the token premium dominates. The picture is therefore mixed:
\emph{the tool is cost-effective where the model cannot do the task without it}, and
a token-priced luxury where it can. Because cost-of-pass is a
token \emph{ratio}, it is invariant to the per-token price: at representative commodity serving
rates (order \$0.1--\$1 per million tokens) the absolute cost is a fraction of a cent per correct
answer on the floored tasks, but the comparative verdict does not turn on that rate. We report token
cost rather than wall-clock latency because the batched server multiplexes trials, so per-trial
latency is not recoverable from our logs; a concurrency-one benchmark is the right future
instrument for the time axis. (The output
cap right-censors long generations; raw ``hit-cap'' rates are not comparable across
arms, since tool runs are multi-turn: a cap-hit
on a final narration turn does not void the tool's verified result, so
cap-hit-and-failed stays
$\leq$10\% in the tool arms at the mechanism layer, though the same cap-hit can
censor or fail the delivered answer. We report totals; a completion-only view, which
makes the tool look better, we do not report.)

\subsection{Robustness: Reasoning Mode and Contamination}
\textbf{Reasoning mode.} At the mechanism layer, the same signed rule applied to
the \emph{think}=on
corpus reproduces the \emph{think}=off mechanism-layer pattern; the delivered surface under
\emph{think}=on carries the same censoring bounds as at \emph{think}=off and adds
no decided cell. But the raw \emph{think}=on
gaps are budget-confounded: reasoning and answer share one decode budget
($6{,}144$ tokens; $8{,}192$ for \emph{solve}), and $14$--$92\%$ of $\geq$9B
no-tools \emph{think}=on trials truncate (Gemma-MoE-26B $92\%$, the 35B only $14\%$), collapsing the validation baselines
(\emph{validate\_plan}: 9B $80\!\to\!21\%$, Gemma $88\!\to\!10\%$;
\emph{validate\_domain} Gemma $78\!\to\!0\%$). We therefore read the cross-mode
evidence only through budget-insensitive statistics. The steered tool arm is
mode-stable at the mechanism layer (mean off-vs-on shift $9$\,pp; the 35B is
invariant on all five tasks)
while the no-tools baseline swings $28$\,pp, so nearly all cross-mode movement
is a baseline effect rather than a change in the tool's value. The robust floor (the
minimum benefit over both modes, computed at the mechanism layer) keeps
\emph{solve} robust ($+46$--$71$\,pp) and
\emph{simulate} sole-source on the format-exact grade ($+83$--$97$\,pp; a benefit with no baseline cannot be
budget-confounded); the \emph{validate\_*} tasks are budget-dependent, their large
\emph{think}=on gaps being the artifact.

\textbf{Contamination.} Because the domains are public, we re-ran the matrix on
structurally identical domains with all surface names renamed
(Table~\ref{tab:contam}). Paired trial by trial, the \emph{think}=off no-tools rates
of the two corpora meet the $\pm5$\,pp criterion for every model when pooled over the
five tasks (the widest interval is Qwen3.5-4B's, $-2.0$\,pp, $[-4.3, +0.3]$), so we
detect no memorization effect on the unaided baseline. The pooled rate is dominated by
\emph{validate\_plan} ($3{,}000$ of $4{,}560$ trials), so the per-task breakdown
(Table~\ref{tab:contam-pertask}) carries more information. Across the $15$ $\geq$9B
(model\,$\times$\,task) cells the mean $|\Delta|$ is $1.2$\,pp (max $3.7$). The
criterion is met in $10$ cells, $6$ of them at a floor or ceiling where they say
little, and not met in $5$ (\emph{validate\_domain} for all three models,
\emph{validate\_problem} for Qwen3.5-9B and Gemma-MoE-26B). In each of those five the
renamed corpus scores higher, the opposite of the direction memorization of the public
domains would produce, and no per-task interval admits a canonical advantage of
$5$\,pp or more. Under \emph{think}=on the criterion is not met for Qwen3.5-4B,
Qwen3.5-9B and Qwen3.6-35B: pooled, the renamed corpus scores $2.7$ to $4.6$\,pp
lower, the direction memorization would produce. In this mode the shared budget
truncates many trials, and the renamed prompts run $\approx$5\% longer. In
\emph{validate\_plan}, where the two corpora's $95\%$ intervals separate, success falls
$4$--$6$\,pp in lockstep with completion while success-given-completion is unchanged,
so that cell traces to tokenization rather than memory. This is itself a
demonstration of the budget confound above.

\textbf{A budget-decoupled control.} Because the shared decode budget confounds the
\emph{think}=on unaided baseline, we re-ran the unaided arm under the decoupled
apparatus described in the \emph{simulate} results (separate reasoning and answer
allowances; Qwen roster; a separate corpus, never pooled with the canonical sweep).
Beyond the \emph{simulate} recovery reported there ($22$--$40\%$ content-correct at
$\geq$4B), validation baselines rise sharply (e.g.\ \emph{validate\_plan}
$+34$--$60$\,pp for 4B/9B, Wilson-disjoint), while \emph{solve} is flat for 9B/35B
and drops $6$\,pp at 4B, so decoupling is not uniformly beneficial. The tool
verdicts are unchanged; what shrinks is the unaided floor.

\textbf{A frontier proprietary model.} To test whether these baseline properties
hold beyond the open-weight roster, we re-ran the no-tools arm on Claude Sonnet 4.6,
a strong proprietary model, over both corpora at full $N$ (\emph{think}=off;
Table~\ref{tab:frontier}). The \emph{solve} floor carries over: unaided success is
$28.7\%$, above the open-weight roster's $8$--$11\%$, so the frontier model retains modest
unaided planning ability but still fails on more than two thirds of problems without
the tool. The \emph{simulate} floor does not carry over: after de-censoring from the raw
batch output, Sonnet's unaided canonical cell is \cbnd{41.7}{61.3} ($59$ of
$300$ still indeterminate) and its anonymized cell \cbnd{36.3}{57.7}, both far
above zero at the claim-adverse end and consistent with the budget-decoupled
open-roster control
($22$--$40\%$ at $\geq$4B; Results). Unaided state tracking grows with model
capability once format and budget pressures are removed; the open-weight roster's
apparent zero reflects those pressures ($68\%$ unparseable, $29\%$ truncated;
Figure~\ref{fig:failtax}) and does not carry over to the stronger model. On
contamination the frontier comparison says less than the open-weight one. Paired
trial by trial, the three validation tasks meet the $\pm5$\,pp criterion
(\emph{validate\_domain} $-1.9$\,pp, \emph{validate\_problem} $+0.8$,
\emph{validate\_plan} $+0.0$), but two of them sit at a ceiling. \emph{Solve} is
unresolved: its totals agree ($28.7\%$ and $28.3\%$), yet its $90\%$ interval,
clustered by domain, is $[-10.6, +9.9]$\,pp, because single domains move in both
directions under renaming (\emph{blocksworld} falls from $11$ to $3$ of $15$ solved
answers, \emph{tpp} rises from $0$ to $6$). With one renaming per domain we cannot
tell a memorized domain from a harder renaming, so we report no memorization effect
at the frontier, and no equivalence on \emph{solve} either. The \emph{simulate}
cells are censoring bounds on both corpora and their bounds overlap broadly, so
no drift is claimed there, while noting it is the one cell a stronger
contamination design should revisit.

\textbf{Frontier with-tools: the lift shrinks as the model strengthens.} The
frontier corpora also carry a with-tools arm (canonical corpus, one paraphrase
bank), and because their delivered rates are exact they give the cleanest
end-to-end availability gaps in the paper. On the validation tasks the
delivered lift is large for Haiku ($+10.8$ / $+23.5$ / $+7.3$\,pp on
\emph{validate\_domain} / \emph{problem} / \emph{plan}, all CI-disjoint) and
shrinks by half to three quarters for Sonnet ($+2.5$, not separated / $+11.5$ /
$+2.9$\,pp), so the tool's headroom on tasks the model partly does closes as
the model strengthens. \emph{Solve} is the counterpoint: the delivered lift is
large at both tiers ($22\!\to\!95$ and $29\!\to\!95$) because the unaided
floor barely moves. On \emph{simulate} the with-tools bounds
(\cbnd{49}{62} Sonnet / \cbnd{52}{64} Haiku) are not separated from Sonnet's
unaided \cbnd{41.7}{61.3} at full $N$ (\cbnd{34}{53} on the matching
prompt-v11 slice), so no delivered lift is claimed there; the tool's work shows
up at the mechanism layer ($97$--$99\%$) and is lost in delivery, as the delivery-gap
analysis showed. These runs corroborate the unaided baseline structure and the
delivery-gap pattern at the frontier; the invocation-rate findings remain
specific to the open-weight roster (both frontier models call the tool on
essentially every trial).

\section{External Validity on PlanBench}
\label{sec:planbench}
All the results so far come from one test suite, and in that suite the PDDL files are
handed to the model inside the prompt. We wanted to know whether the same pattern
appears on a benchmark that someone else built, so we repeated a smaller version of the
experiment on PlanBench \citep{valmeekam2023planbench}. We use its plan-generation task
in two domains. The first is standard Blocksworld. The second is Mystery Blocksworld,
which renames every predicate and action to an unrelated word and leaves the underlying
problem untouched. The instance files sit in two directories of $501$ and $101$ files,
and the first file in each serves only as the worked example, which leaves $500$ and
$100$ instances to ask. We checked all $602$ files and confirmed that the
renaming is a straight symbol swap with the objects unchanged, so the two domains ask
the same planning question in different words. Every cell uses the same $600$ instances,
and the model is Claude Haiku 4.5 throughout.

One difference from our own suite matters more than the change of domain. PlanBench
prompts are written in plain English, so a model that wants to use a planner has to
write the PDDL itself first. Our suite hands the files over and never tests that step.
We also grade differently here. A trial counts as correct only when the plan in the
model's final answer is valid, so a correct tool call that the model never copies into
its answer is scored as a failure.

We report two results. The main one uses no tools at all and asks where a current small
model stands on the field's own benchmark next to the published GPT-4 figures. The
second compares tools against no tools, and we treat it as a secondary finding. That
tools can rescue planning on the renamed domain is already published
\citep{huang2025limit}. What we add is the control that earlier work did not report: a
no-tools arm that keeps exactly the same prompt and removes only the tools. We also add
a third arm that keeps the tool instruction but attaches no tools, paired significance
tests with confidence intervals, a measurement of how faithfully the model writes the
PDDL, and the measured dollar cost.

\subsection{The Benchmark Without Tools}
Table~\ref{tab:pb-nt} shows the no-tools results. On standard Blocksworld the model
solves $43.8\%$ of the $600$ instances. The bottom of its confidence interval, $39.9\%$,
sits above the top of the published GPT-4 interval, which ends at $38.2\%$ around a
figure of $34.3\%$, so the two do not overlap. We
describe that gap and do not test it, because the GPT-4 figures come from a different
model generation, a different grading setup, and a corpus we did not run ourselves. On
Mystery Blocksworld our model gets $4$ of $600$ right, which is $0.7\%$. The published
GPT-4 figure on that domain is $4.3\%$, slightly above ours, and both are close to zero.

\subsection{Adding the Tools}
In the with-tools arm the model can call the same planners and validators used in the
rest of the paper, over the same protocol. Its prompt carries a short system message
that tells it to write PDDL first and gives the answer format. The control arm uses that
same system message word for word and simply has no tools attached. Because the wording
is identical on both sides, any difference between them comes from the tools rather than
from what the model was told.

Table~\ref{tab:pb-wt} gives the four cells. On Mystery the gap is as wide as the
benchmark allows, $71.8\%$ with tools against $0.0\%$ without. On standard Blocksworld,
where the control arm already reaches $47.8\%$, tools still lift the cell to $68.3\%$,
an increase of $20.5$ points. Both
comparisons are paired on the same instances and tested with an exact McNemar test. On
Blocksworld, $202$ instances were solved only with tools and $79$ only without, giving
$p=1.4\mathrm{e}{-}13$. On Mystery the split is $431$ to $0$, giving
$p=3.6\mathrm{e}{-}130$.

The Blocksworld with-tools figure is the cautious reading. The run was interrupted and
$18$ instances were asked a second time. On their first attempt all $18$ had used up
their tool-calling turns and returned nothing, so we count them as failures. Reading
them the other way would raise that cell by $1.4$ points.

Once the tools are available the renamed domain is not harder than the standard one.
Inside the with-tools arm the paired gap between the two domains is $3.5$ points in
Mystery's favor, with $119$ instances solved only on Blocksworld and $140$ only on
Mystery ($p=0.214$). Our preregistration listed this comparison as exploratory and named
a paired equivalence test for it, with a margin of $\pm7.5$ points. We declare a deviation here: at readout only the point
estimate was compared with the margin, and the test itself was not computed. We report
it now. The $90\%$ interval for the gap is [$-7.9$, $+0.9$] points and the test gives
$p=0.068$, so the criterion is not met at $\pm7.5$ and the question is unresolved at
that margin. The preregistration also names $\pm10$ points for the same comparison, as
a requirement of its mechanism check, and at $\pm10$ the criterion is met ($p=0.008$).
The interval is wide because the two domains disagree on $43\%$ of instances. The small
gap also depends on a notation loss in the Mystery cell. With the corrected extractor
of Section~\ref{sec:pb-distort}, Mystery is $24.2$ points higher.

\subsection{What the Tools Actually Fix}
The natural explanation for the Mystery collapse is that renaming the vocabulary breaks
the model's ability to search for a plan. Our with-tools data point somewhere else. For
every trial we recovered the PDDL the model sent to the planner and compared it against
a correct reconstruction of the same instance, using a parser we deliberately kept out
of the model's own tool set. The model's PDDL captures the intended meaning on $96.3\%$
[$94.5$, $97.6$] of standard trials and $97.8\%$ [$96.3$, $98.7$] of Mystery trials, so the
renaming does not damage it.
Turning an English description into PDDL is a copying job that does not depend on what
the words mean, and unfamiliar names leave it intact. Every with-tools trial in both
domains called the planner.

The same measurement shows what still holds the standard cell back. When the model's domain
file carries the intended meaning, the planner returns a solvable problem $99.5\%$ of
the time. When it does not, that falls to $1.6\%$, and none of the $35$ mismatched
trials produced a correct plan. The limit is how faithfully the model writes the domain,
and the reason is visible in the English source. The standard Blocksworld description
leaves out part of the physics, never saying that moving a block leaves the one beneath
it clear, and the model writes down what the text says. The Mystery text is a mechanical
rendering of the same rules, which is why $99.5\%$ of Mystery domains come out right and
the renamed cell scores a little higher than the standard one.

This adds a step to the failure sequence we track for our own tasks. When the prompt
already contains PDDL, a with-tools trial can fail in three ways: the model never calls
the tool, it calls with bad arguments, or it fails to report what came back. PlanBench
puts an earlier step in front of those: can the model write the problem down in the
tool's language at all? We treat \textsc{formalize} as the first stage of the PlanBench
sequence (Figure~\ref{fig:funnel}, top right, draws all four stages), and it belongs to
the benchmark, because it cannot arise anywhere the PDDL is supplied. Once a plan clears that stage and the extractor, the delegated search is right
$95.9\%$ of the time on Blocksworld and $97.3\%$ on Mystery.

\subsection{What Could Distort These Numbers}
\label{sec:pb-distort}
Several measurement problems affect these cells. The figures we report as primary
correct for none of them, as preregistered. For the two that come from the plan
extractor we add a post hoc regrade at the end of this section. Most
work against the tools arm. On Mystery, $125$ of $569$ delivered plans were thrown out
because the model wrote its actions in a PDDL shorthand the benchmark's extractor does
not read. Trials that used
up their tool-calling turns without answering are counted as failures, which costs the
standard and Mystery with-tools cells $10.5\%$ and $5.2\%$ of their trials. Failures to
write usable PDDL are charged to the model as well.

One problem works the other way, and it affects the cell we report as $0.0\%$. In $479$
of the $600$ Mystery no-tools trials, the model wrote out its reasoning in a way that
leaked extra actions into the plan the extractor picked up, which spoils plans that
would otherwise have been graded. Reading only the text inside the model's own answer
block gives $26$ of $600$, or $4.3\%$ [$3.0$, $6.3$] (coincidentally equal to the
published GPT-4 figure), and we report both figures. The
leak pushed the no-tools cell down, so this problem worked against the published $0.0\%$
instead of inflating our result. The comparison with the tools arm survives either
reading. Under the stricter one, $412$ instances are solved only with tools and $7$ only
without, giving $p=6.4\mathrm{e}{-}112$. Two further measurements
agree that the collapse is real. The $121$ trials with no leak score $0$ of $121$, and
the published prompt, which carries no system message and shows no leak, scores $0.7\%$.

After the readout we wrote a corrected extractor and regraded all four cells with it.
It reads only the model's final answer block, and it accepts the PDDL shorthand as well
as the English phrasing. Every plan it extracts is checked by the same validator
against the same instance files. This regrade is post hoc and was not preregistered,
so the figures above remain the primary result. The corrected figures are $47.8\%$
[$43.9$, $51.8$] without tools and $70.2\%$ [$66.4$, $73.7$] with tools on Blocksworld,
and $4.3\%$ [$3.0$, $6.3$] and $94.3\%$ [$92.2$, $95.9$] on Mystery, where $566$ of
$600$ trials deliver a valid plan. All $125$ shorthand plans are valid, and no trial moved
from correct to incorrect. Both tool contrasts grow, to $22.3$ points on Blocksworld
($207$ instances solved only with tools and $73$ only without,
$p=5.1\mathrm{e}{-}16$) and to $90.0$ points on Mystery ($541$ and $1$,
$p=7.5\mathrm{e}{-}161$). The comparison between the two domains changes more. With
the corrected extractor the with-tools gap is $24.2$ points in Mystery's favor, with
$28$ instances solved only on Blocksworld and $173$ only on Mystery
($p=1.0\mathrm{e}{-}26$), and the equivalence criterion is not met at either margin.
The notation loss fell almost entirely on the Mystery cell, which is what brought the
two primary figures close together. Our prompt asked for the English phrasing, so a
shorthand answer is still a failure to follow the instruction, and the primary grading
counts it as one.

\subsection{Scope and Cost}
This arm covers one model. We registered a stronger second model as an extension and did
not run it, so we cannot say how the tools gain changes with model strength on this
benchmark, and the comparison with GPT-4 in Table~\ref{tab:pb-nt} rests on a single
model of ours. Measured cost was \$$39.87$ for the $2{,}400$ trials of the main
comparison and \$$2.61$ for the instruction-only arm. The whole PlanBench arm came to
about \$$46$ including the calibration runs, or roughly \$$0.017$ per trial.

\section{Discussion}
\paragraph{What the three answers say together.} A sound tool guarantees its own
result. What a user receives depends on two further steps that the guarantee does not
cover: the model has to call the tool, and the tool's result has to reach the final
answer. RQ2 and RQ3 measure these two steps, and RQ1 measures their combined effect.
Where both steps hold, the benefit is large: the models deliver a valid plan in
$77$--$95\%$ of the trials with the tools, against $21$--$29\%$ without. Where the
first step fails, the tools change little. Gemma-MoE-26B calls the plan validator in
$20.0\%$ of the plain-prompt trials, and its verdict errors with the tools offered are
close to its unaided ones. Where the second step fails, the tools can make the answer
worse. The same model calls the state-transition tool in $99.7\%$ of its trials, loses
$90.8\%$ of the correct traces it gets back, and ends with fewer exact traces than it
produces unaided.

\paragraph{Choosing the tool.} On the validation tasks and on \emph{simulate} the
models rarely pick a wrong tool. The open issue there is whether they call at all, and
one sentence that names the tool closes most of that gap in every model we measured.
On \emph{solve} the models call more than the task needs. Much of the addition is a
check of the planner's plan, which costs tokens and does not harm the answer. Calling
the planner that does not fit the domain is a different matter: a numeric planner
still returns a valid plan for a classical problem, and that plan can be far longer
than the reference. With thinking on, two of the three larger open-weight models call
the right tool less often, so reasoning mode and tool calling are not independent
settings.

\paragraph{Using the output.} A verdict is a single word and almost always survives.
A plan or a state trace has to be restated in the answer, and the loss grows with the
length of what must be restated. In the open-weight runs the largest registered cause
is a final turn that was refused or cut because the conversation, which already held
the tool's result, had filled the context window. This suggests that the loss depends
on how much room the answer has left, and less on the content of the tool's result. We
did not vary the window size or the output allowance in these runs, so we state this
as a reading of the registered categories and leave the test to future work.

\paragraph{Unaided planning.} Our unaided models solve $21$--$29\%$ of a set of small
problems, with thinking off and a prompt without solved examples. \citet{correa2025frontier}
report that frontier reasoning models, prompted with two solved examples, rival strong
planners on larger and freshly generated tasks. The two studies differ in models,
reasoning mode, prompt and problems, so our unaided figures describe the models and
settings we ran and should not be read as a general limit on what language models can
plan. Our question starts where theirs ends: what changes when the same model may call
a planner.

\paragraph{For practice.} Three observations follow for a system that puts a planner
or a validator behind a tool interface. Offering the tool is not enough for every
model, and a sentence that names it is a cheap repair. A model that calls several
tools on one task may call a planner that does not fit the domain, so the choice of
planner is worth constraining. A tool whose output the model must restate needs room
in the context window for that restatement.

\section{Limitations}
Several constraints bound these conclusions. The measures of RQ1 and the
classification of RQ2 were defined after the data were collected, so they are
exploratory; only the loss categories of RQ3 on the rerun were registered. The
comparisons that need the complete final answer cover five models: three open-weight
models with thinking off, and two Claude models on a single prompt wording. The rerun
behind them did not meet its registered parity criterion against the main sweep, so it
is reported as a separate replication and its figures are never pooled with main-sweep
figures. The planner solves every problem of the test set, so the results do not cover
problems that the planner itself cannot solve, and its runtime barely separates the
problems; hardness is therefore measured by plan length. The reference plans are the
planners' first plans and are not shortest plans, so the plan-length comparison is
against a common baseline and makes no claim about optimality. Claude answers were
stored up to $16{,}384$ characters, so Claude figures on \emph{simulate} are lower
bounds where storage cut the answer. Under \emph{think}=on, reasoning and
answer share one decode budget, so a large fraction of no-tools trials truncate; we
defend the cross-mode claims with budget-insensitive statistics (the robust floor),
but cannot fully decouple the tool's value from the budget in that mode. A naive cap increase is
not a clean remedy: in pilot runs, enlarging the shared decode budget (a larger common
allowance, not a cap reserved separately for the final answer) degraded output-format adherence
(more trials emitted unparseable answers), so it trades the truncation confound for a parsing one
rather than removing it, which is again why we read cross-mode evidence through the budget-insensitive
robust floor. Decoding is deterministic (temperature~0), so each
trial is a single sample and our intervals quantify uncertainty over the fixture
instances, not decoding variance; robustness to higher temperatures is untested.
The roster is five open-weight models from two families, so our claims concern the
\emph{regime structure} of when a tool helps these models rather than a leaderboard.
The unaided side of that structure partially extends to a strong proprietary model:
Claude Sonnet 4.6 reproduces the \emph{solve} floor (with no detectable memorization
effect, although its \emph{solve} comparison across corpora is unresolved), while
on \emph{simulate} it recovers substantial unaided success (\cbnd{41.7}{61.3}),
consistent
with the budget-decoupled control on the open-weight roster ($22$--$40\%$), so that task's
apparent floor is an apparatus effect rather than a capability constant
(Table~\ref{tab:frontier}). The with-tools invocation-rate finding, however, was
measured only on the open-weight roster, so whether the availability gap and its
one-sentence steering repair transfer to proprietary models with aggressive tool-use
post-training is untested here. The fixture suite of $20$ domains spans
classical and numeric planning but does not cover all of PDDL's features (temporal, durative, and
conditional-effect constructs are absent), so the regime boundaries we report may shift on richer
formalisms. Model scale is moreover
partially confounded with numerical precision (the two largest models are served
AWQ-INT4 while the smaller three are 16-bit), so the cross-model plain-arm size
inversion cannot fully separate a model's spontaneous invocation rate from a quantization
effect on tool-calling; we therefore frame the invocation rate within-model, through the
$P(\text{call})\times P(\text{correct}\mid\text{call})$ decomposition, which does not
rest on that comparison. The availability gap likewise differences two arms whose
system prompts, beyond tool presence, also differ by a one-line policy/format clause,
so the steering gap (where the plain and steered prompts differ by exactly one
appended sentence) is the cleaner of the two contrasts. The control that
supports the tool-use reading of the steering effect (Results) does not
establish it causally. Its no-tools system prompt states that tools are
unavailable while the appended directive names one, so the control removes both
the tool and its stated availability, and that contradiction biases the test
toward equivalence. Its verdicts cover the six pooled units and the eight
eligible task cells, and the task cells excluded by the eligibility gates
remain unresolved. The two figures compared in the matched cell are read at
different layers, the with-tools effect at the mechanism layer and the control
on the model's own answer, so the comparison is a juxtaposition across
surfaces. The control was run on a later apparatus than the canonical sweep,
beside a neutral-prompt arm in the same job, so its bearing on the canonical
steering gap rests on how closely that neutral arm reproduces the
canonical no-tools rates (within $1$\,pp pooled, Technical Appendix) and on the
unmeasured run-to-run variation of deterministic decoding, since no prompt was
ever sampled twice under one apparatus. No \emph{think}=on control exists for
Gemma-MoE-26B, whose \emph{think}=on unaided cell saturates the decode budget
under every apparatus available to us. Grading of the model's own
text is strict by design (format adherence is part of the task), so a model that
reasons correctly but emits malformed output scores as a failure; we report the
failure-type decomposition, and the budget-decoupled control (Results), so this is
visible rather than hidden. The no-tools arm was meant to decode under a per-task
JSON schema, but an audit of the stored responses shows that the constraint never
took effect: of the $58{,}581$ validation responses on which this can be established
across the canonical and anonymized corpora, none contains JSON of any kind, and
schema conformance over all five tasks is $0.36\%$ of $65{,}874$ such responses
($1.92\%$ of the $12{,}176$ stored in full), so the \emph{solve} and \emph{simulate}
prompts pointed the model to a schema ``provided by the format constraint'' that it
never received, the unaided results on those two tasks were obtained under a
prompt-level format instruction alone, and what a working constraint would have
produced is unmeasured. The largest self-imposed constraint is storage: the
open-roster corpora stored final answers as $500$-character snapshots, a decision
made before the delivered surface was fixed as primary, so the tool arms'
delivered rates there are censoring bounds and several availability cells are
undecided rather than measured. The pre-registered rerun stores answers in full for the
three $\geq$9B models with thinking off and is what RQ1 and RQ3 rest on; the main-sweep
cells themselves stay bounds, because the rerun did not meet its parity criterion and
cannot stand in for them. The frontier
\emph{simulate} cells have been probed with a larger allowance (Supporting Analyses):The frontier
\emph{simulate} cells have been probed this way (Results): under a $64$K
allowance with full storage they become exact, the budget explanation is
confirmed at one tier and only partly supported at the other, and the residual
failures ($30$--$35\%$ of tool-arm trials) are wrong or unparseable trajectories
rather than truncation, so a larger allowance narrows the gap without closing it. The serving
runtime did not surface per-trial reasoning traces for the model family used, so
\emph{think}=on reasoning is evidenced through completion-token counts rather than
archived chains of thought; and wall-clock latency is not recoverable from a
batched server, so we use token cost, not time, as the efficiency axis. Finally,
\emph{validate\_domain} carries a $5{:}1$ positive-to-negative imbalance that
widens its negative-arm interval; we therefore headline balanced accuracy for that task, which,
like $F_1$, is robust to the imbalance that a pooled metric would reward.

\section{Future Work}

follow directly from the limits of the three research questions; the earlier list

Four extensions follow from the limits above. The first is a test set that includes
problems the planner cannot solve within its time limit, so that the benefit of the
tools can be followed past the point where the planner itself gives out. The second is
the tool arm for reasoning models, which we ran only in the main sweep, where answers
were not stored in full. The third is a direct test of the reading in RQ3, by varying
the room that the context window leaves for the final answer. The fourth is the same
three questions on planning formalisms that our test set does not cover, such as
temporal planning.

\section{Conclusion}
We asked three questions about giving a language model sound PDDL tools. The tools
help on most of what we measured: valid plans rise from $21$--$29\%$ of the trials to
$77$--$95\%$, and verdict errors on plans fall for four of five models. The benefit
shrinks as problems grow, and state traces degrade with length with or without the
tools. The models usually choose the right tool, with two qualifications: one model
seldom calls the plan validator until a sentence tells it to, and on plan generation
the models add calls, some of them to a planner that does not fit the domain. The step
that fails most often is the last one. A correct verdict almost always reaches the
answer, a correct plan is lost in $5$--$13\%$ of the trials, and a correct state trace
is lost in most of them, largely because the tool's result leaves no room in the
context window for the answer. A planner or a validator behind a tool interface
therefore helps a language model most when the model is told to call it, calls the one
that fits the task, and has room to deliver what it returns.

\paragraph{Execution protocol of the output-budget probe.}
The probe (Results, Delivery Gap) was pre-registered, and its analysis code was
frozen by hash, before the first API call. Each tier re-ran the $100$ canonical
\emph{simulate} trial keys of its with-tools cell under the same prompt
(v11), temperature~$0$, the same tool loop (at most ten calls), and the same
pinned ground truth, changing two settings: the per-turn output allowance,
$64{,}000$ tokens on both tiers (Haiku~4.5's output ceiling, so both tiers share
one value), and the stored response, $262{,}144$ characters, which no probe
answer reached. Each run wrote a manifest of its settings before its first
request, and a resume into a directory whose manifest differed was refused. The
no-tools arms were run at the same allowance through the provider's batch
interface. The primary test is a one-sided Fisher exact test comparing conversion
among the canonical cell's truncated, budget-fitting failures (Sonnet $25$, Haiku
$17$) against its non-truncated failures re-run under the same apparatus (Sonnet
$19$, Haiku $12$), with a confirmation criterion of $p<0.05$ and at least $60\%$
conversion. One infrastructure failure (a Sonnet trial that raised an exception
before producing any tokens) was retried under the runner's existing resume
policy; the completed retry was graded incorrect, and the primary verdicts were
unchanged. No probe answer was censored by storage; no tool-arm final turn reached
the allowance (one Sonnet and two Haiku no-tools answers did). Measured cost of
the four cells was \$40.68.

\paragraph{The steering control.}
The control arm of the Methodology (the steering directive with the tools
removed) was pre-registered as an equivalence test before it was run, after the
main sweeps, in six (model, mode) units: Qwen3.5-4B, Qwen3.5-9B, Gemma-MoE-26B
and Qwen3.6-35B at \emph{think}=off, and the two Qwen models at
\emph{think}=on. Each unit is one job of $9{,}120$ trials: the three neutral
paraphrases of every task (the \emph{anchor}, $4{,}560$ trials) and the same
paraphrases with the directive of Listing~\ref{lst:prompts} appended
($4{,}560$ trials), interleaved by one process against one server, with the
no-tools system prompt unchanged. The \emph{think}=on units use the
budget-decoupled apparatus of the Results with the serving runtime's reasoning
parser off (see the deviations below). The two modes are separate apparatuses,
and no number is compared across them. Gemma-MoE-26B has no \emph{think}=on
unit, because its \emph{think}=on unaided cell saturates the shared decode
budget and the decoupled apparatus relies on a reasoning delimiter that model
does not emit. The hypothesis is that the directive alone moves the no-tools
rate by less than $5$\,pp. The surface is the model's own answer (delivered) on
determinate rows. Rows censored at the $16$K storage cap ($1.2$--$1.7\%$ per
unit, all \emph{simulate}) are excluded from every estimator and reported as
bounds. The estimate is the paired difference, steered minus anchor, over
$4{,}466$--$4{,}500$ matched trial pairs per unit, with $90\%$ intervals
clustered on domain ($k{=}20$) and on problem instance (size-weighted, realized
$k{=}220$). The wider interval governs. A unit passes if its pooled interval
lies inside $(-5,\,+5)$ and no eligible task cell has an interval entirely
outside it. The paper-level claim requires every unit to pass, an
intersection-union test that needs no multiplicity correction. A task cell is
eligible when its anchor rate lies in $[10\%,\,90\%]$, its realized
domain-clustered half-width is at most $5$\,pp, and its own paraphrase noise
floor $F$ is below $5$\,pp, where $F$ is the largest absolute difference among
the three designed-null pairs of neutral paraphrases in the anchor arm. A cell
whose $F$ reaches the margin is uninformative at that granularity and cannot
contribute a failure, because the paraphrases alone move it by more than the
effect under test. This gate removes \emph{solve} ($F$ of $14$--$31$\,pp),
\emph{simulate} ($5.6$--$36.3$\,pp) and \emph{validate\_domain}
($5.0$--$14.2$\,pp) in every unit. The registered threshold for declaring a
unit not-equivalent is $5$\,pp plus its realized governing half-width (MDE in
the tables): the smallest $|\hat\Delta|$ at which the interval would lie
entirely outside the margin.

\emph{Within-corpus factorial diagnostic.} The preregistration also fixed an
optional replication check on the two \emph{think}=on units, whose no-tools
legs come from the control run and whose with-tools legs come from the
independent full-storage rerun (Results), two runs under one apparatus pin.
The estimand is the interaction
$\Delta_{\text{wt}}(\text{steered}-\text{neutral})-
\Delta_{\text{nt}}(\text{steered}-\text{neutral})$ per model, on the delivered
surface for both legs with the same clustered $90\%$ interval, and the
attribution counts as replicated for a model when that interval excludes zero
and its sign matches the model's canonical \emph{think}=on with-tools steering
effect. The replication clause was to enter the main claim only if every model
met the criterion. Fixtures censored on either leg are excluded ($3{,}765$
matched fixtures for Qwen3.5-9B, $4{,}417$ for Qwen3.6-35B). For Qwen3.5-9B
the interaction is $+8.12$\,pp $[+4.61,\,+11.63]$ (with-tools steering
$+8.54$\,pp against no-tools $+1.87$\,pp), and its sign matches the canonical
$+11.38$\,pp, so the criterion is met. For Qwen3.6-35B the interaction is
$+2.62$\,pp $[+0.74,\,+4.50]$ (with-tools $+2.05$\,pp against no-tools
$-0.47$\,pp), but its canonical reference effect is $-0.11$\,pp, an essentially
null reference whose sign cannot meaningfully be matched, so the criterion is
not met. The per-model criterion therefore fails, and the replication clause is
not carried into the main claim, as pre-registered. The diagnostic is bounded
in three ways that the preregistration stated in advance. Gemma-MoE-26B, the
model that owns the $+72.0$\,pp, cannot be in it, because it has no
\emph{think}=on no-tools leg. The factorial is \emph{think}=on while the body's

corpus was co-run with the control. And the two legs are budget-unmatched by
construction, since the tool loop re-grants the per-task decode budget on every
turn (up to ten calls) while a no-tools trial has one shared budget, so the
comparison was declared attribution-only and no rate from it is quoted as an
effect size. Descriptively, both interactions are positive and exclude zero,
which is consistent with the tool-use reading. On \emph{validate\_plan} alone
the interaction is $+15.0$\,pp $[+9.0,\,+21.0]$ for the 9B and $+2.8$\,pp

and a per-task cell carries no clause authority.

\emph{Deviations from the preregistration, declared.} Three changes were made
after the preregistration was ratified. First, the control roster was expanded
from three models to four after interim results were seen. The preregistration
fixed the roster at Qwen3.5-9B, Gemma-MoE-26B and Qwen3.6-35B. With those three
\emph{think}=off units complete and passing, we measured the with-tools steering
effect the control was designed to test across the full roster at the mechanism
layer and found that Qwen3.5-4B carried a larger effect ($+6.9$\,pp pooled,
$+9.6$\,pp on \emph{validate\_plan}) than the controlled Qwen3.5-9B
($+2.5$\,pp), while Qwen3.5-0.8B showed no pooled effect ($+0.0$\,pp) and so
gives the control nothing to test. We added a Qwen3.5-4B \emph{think}=off unit with apparatus
parity to the three completed units. It passes. Under the intersection-union
rule a fourth unit can only make the conjunctive claim harder to satisfy, and
the unit was chosen by the size of its with-tools steering effect, before its
control result was known. Second, the \emph{think}=on arm was rerun with the
reasoning parser off. The preregistration ruled that the parser override is not
passed, reasoning about the single-call path in which reasoning and answer
share one output stream. The \emph{think}=on units use the two-call decoupled
apparatus, and under that rule it produced a void corpus: $9{,}120$ of $9{,}120$
and $3{,}822$ of $3{,}824$ rows with empty answer text, no errors, and about
$13$K tokens generated per row. We cancelled the arm, discarded the void rows
(retained as a failure record), and reran with the parser off, the setting
under which that apparatus had been validated. The rerun reproduces an earlier
parser-off run of the same two models under that apparatus to within a
percentage point on both empty-text share ($8.2\%$ and $3.9\%$ against $8.8\%$
and $4.1\%$ predicted) and success rate ($69.1\%$ and $82.5\%$ against $68.4\%$
and $82.0\%$), and the grading artifact the original rule guarded against does
not appear on this path (unparseable answers are $0.0\%$ on all three
validation tasks in all four affected arms). The two modes were already
declared separate apparatuses whose numbers are never compared, so the change
alters no comparison. Third, after the first readout was ratified, a code
review of the hash-frozen analysis found defects: rows censored at the storage
cap had been scored as successes on the delivered surface, the problem-instance
clustering assumed $100$ balanced clusters where the fixture layout yields
$220$ unbalanced ones and so estimated a task-reweighted quantity, and the
secondary mechanism decomposition read fields the graded rows do not carry. The
code was corrected, re-frozen by hash, and the analysis regenerated from the
checkpointed corpus. The corrected analysis preserved all six unit verdicts and
the paper-level branch. The figures reported here are the corrected values.

\paragraph{Canonical trajectory normalization (\emph{simulate}).}
A \emph{simulate} answer is graded by deep-equality against the oracle trajectory
after a canonical normal form is applied to both, so the open-weight roster's $0\%$
unaided rate is not an artifact of predicate notation in the grader. Per state, the boolean predicate list is
case-folded, whitespace-collapsed, and sorted; predicate atoms are compared in a
notation-neutral form, so an s-expression rendering \texttt{(on a b)} and a
functional rendering \texttt{on(a,b)} match; and numeric fluents are keyed by their
canonical parenthesised form. Case, internal spacing, notation style, and ordering
therefore never affect the verdict;
only the set of true predicates and the fluent values do. For example, an oracle
state whose true predicates are \texttt{(clear c)} and \texttt{(on a b)} is matched by
a model state listing \texttt{(ON A  b)} then \texttt{(clear c)}, and a numeric fluent
\texttt{(fuel t1)} of value \texttt{5} matches \texttt{5.0}; but a single missing or
extra predicate in \emph{any} state fails the entire trajectory.
